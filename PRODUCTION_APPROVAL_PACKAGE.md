## 5. Rollback and limitations
| Layer | Procedure |
|---|---|
| Stop spending | Telegram `/kill` or app kill switch (no deploy needed) |
| Code (Railway) | move the deploy branch back to the previous known-good sha (`--force-with-lease` against the bad sha), per `DEPLOY_RUNBOOK.md` s5 |
| PWA (Render) | `git revert` the merge commit on `overnight-build`, or redeploy the prior Render deploy |
| Database (this release) | `ops/rollback_sprint12.sql` (begin..commit): drops the four migrations' functions/triggers, restores the `queue_prospect_task()` overload set; **tables are left in place** |
| Database (Phase 1) | `ops/rollback_phase1.sql` also removes Phase 1; **do not use for this release** |
Limitations: data/audit rows (suppressions, replies, deals, action_log) are not undone; `contact_suppressions` is append-only by design so the table and its two triggers remain after rollback (preflight row 5 counts only the three named triggers); a rollback is tested on the replica (full apply -> rollback -> re-apply -> e2e), not on production; the PWA must be rolled back together with the database if the RPCs it calls disappear.

Owner-only. Full steps: `BACKUP_SETUP_OWNER.md`, `ops/backup_config_checklist.md`, `BACKUP_PROOF_PROCEDURE.md`. Summary: owner creates the free-tier B2 bucket and a write-only application key (stop if any card/payment is requested), generates `BACKUP_KEY` offline and stores it offline, sets the non-secret variables and the secrets in Railway directly (never in Telegram, ChatGPT, GitHub or reports). **Backup is "proven" only after:** (a) a real production object exists in B2 (owner confirms in the B2 console), (b) it is downloaded, (c) decrypted with the offline key, (d) restored into an isolated local database with `ops/restore_local.sh`, and (e) schema/row-count verification passes. Until then the report says **not proven**. Synthetic replica tests prove the code, not production.
