## 5. Rollback and limitations
| Layer | Procedure |
|---|---|
| Stop spending | Telegram `/kill` or app kill switch (no deploy needed) |
| Code (Railway) | move the deploy branch back to the previous known-good sha (`--force-with-lease` against the bad sha), per `DEPLOY_RUNBOOK.md` s5 |
| PWA (Render) | `git revert` the merge commit on `overnight-build`, or redeploy the prior Render deploy |
| Database (this release) | `ops/rollback_sprint12.sql` (begin..commit): drops the four migrations' functions/triggers, including the `queue_prospect_task(text)` overload (the pre-existing `queue_prospect_task()` is untouched); **tables are left in place** |
| Database (Phase 1) | `ops/rollback_phase1.sql` also removes Phase 1; **do not use for this release** |
Left in place after rollback: tables `contact_suppressions`, `lead_replies`, `venture_config`; the unique index `deals_one_open_per_lead` on `deals` (keeps blocking a second open deal per lead); the `lead_replies` indexes; seeded suppression rows. The `contact_suppressions_address_check` constraint is dropped. Limitations: data/audit rows (suppressions, replies, deals, action_log) are not undone; `contact_suppressions` is append-only by design so the table and its two triggers remain after rollback (preflight row 5 counts only the three named triggers; after a sprint rollback preflight row 4 reads 3 because `evidence_sources` is dropped with its snapshots, which is expected); a rollback is tested on the replica (full apply -> rollback -> re-apply -> e2e), not on production; the PWA must be rolled back together with the database if the RPCs it calls disappear.
