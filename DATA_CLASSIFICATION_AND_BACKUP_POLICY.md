# Data classification, off-site backup and consent — policy as built

Status: ENGINEERING POLICY IMPLEMENTED IN CODE (dev branch, migrations NOT applied to production). Not legal advice. Items marked OWNER/COUNSEL are decisions this document does not make.
Owner decisions this implements (Nov 2026): A consent log, B health terms in the sensitive-data detector, C no client lead PII in off-site backups, D backups only after exclusions are verified.

## 1. What leaves the database, and what never does

| Class | Meaning | Off-site backup |
|---|---|---|
| `public` | non-personal reference data (e.g. published model prices) | exported |
| `internal` | the owner's and the ventures' operating data | exported |
| `client_pii` | third-party personal data: leads, prospects, replies, setters, suppression list, every `ws_*` and `ffm_*` table, `client_workspaces` | **never exported** |
| `secret` | push keys and endpoints | **never exported** |
| unclassified | a table nobody has classified yet | **not exported** (fail closed) until classified in a migration |

Decided by `public.backup_export_policy()` (table NAMES only, never data). Rules, in order of strength:
1. **Deny always wins.** `ws_*`, `ffm_*`, `client_workspaces` are denied by name pattern whatever any list says.
2. **Foreign-key closure.** A table with a foreign key to a non-exported table is not exported (a restore would otherwise load rows that point at missing data).
3. **Column drift.** A table on the allow side that gains a column that looks like personal contact data (email, phone, name, address, payee, birth…) and is not on the reviewed exception list (`backup_pii_column_exceptions()`) is excluded until reviewed.
4. **Second lock in code.** `hq_backup.py` re-checks every table against its own pattern (`ALWAYS_EXCLUDE`) and refuses to write a file if one gets through. It also refuses to run at all if the database function is missing or returns an unexpected result; there is no built-in "export everything" fallback.

The schema (structure, no rows) of every table, excluded ones included, is in the backup so a restore rebuilds the empty tables. The manifest lists what was excluded and why.

## 2. What this does NOT protect (read this before relying on it)
- **The live database and the database provider's own backups still contain client data.** This policy governs only the encrypted off-site file. Provider backups follow the provider's retention.
- **KNOWN LEAK PATHS (confirmed by independent review, NOT fixed in this PR).** The system itself copies client text into tables that ARE exported:
  - `record_lead_reply` / `mark_do_not_contact` put the reply note into `audit_log.detail.reason` (can contain a name, email, phone).
  - `setter_record_payout` writes the setter's real name into `ledger.note` (`setters` is `client_pii`, its name is exported anyway).
  - researcher/outreach output is stored in `tasks.result` (up to 8000 chars, includes prospect names, websites, published emails, outreach drafts); `agent_runs.summary` is free text.
  - Not fixed here because the functions are already live (applied migrations are not edited) and fixing them means redacting at source in a new migration or redacting at export, each with restore-fidelity consequences. **OWNER DECISION required before any backup key exists:** (a) redact these at source, (b) redact these fields at export (restore then loses them), or (c) accept them. The preflight fails until `BACKUP_LEAK_PATHS_ACCEPTED=1` is set deliberately. The drill's P1 check proves absence of the client TABLES only; it does not cover these paths.
- **Free-text in exported tables.** If a person types a lead's details into `memory`, `owner_messages`, `missions` or notes, that text is exported. The detector screens text written through the `ws_*` / `ffm_*` paths only.
- **Column-drift heuristic is best-effort.** It misses names such as `phonenumber`, `contact_name`, `surname`, `cell`, `telephone`, `street`, `postal_code`, `sin`, `msisdn`, `notes`, `recipient`, `customer`. The real control is that every table must be classified by a human in a migration.
- **Restore gap.** After a restore from an off-site file, every client table is EMPTY, including `contact_suppressions`. Before any outreach is ever enabled, the opt-out list must be restored from the provider backup. Never contact anyone from a restored database until that is done.
- **`BACKUP_KEY` / bucket policy** (rotation, who may read, retention) are OWNER decisions not made here. Backblaze is not activated and no key exists.
- Classification is a reviewed list. A mistake there (a client table labelled `internal` and with no suspicious column names) would be exported. The code lock in rule 4 covers the known client table names only. This is why a human review is required when a table is added.

## 3. Consent log (decision A)
- `ffm_consent_log` is append-only and immutable (trigger; `service_role` has no write grants). A withdrawal is a new row, never an update.
- `ffm_can_contact(lead, channel)` is default-deny. True only with a current express consent, or an implied consent inside an owner-set window (`ffm_set_implied_window`, owner-only; unset = implied consent not accepted). A withdrawal (channel or `all`), a suppression hit, a closed workspace, an unknown lead or channel give false. Withdrawal is final in v1. An email or `all` withdrawal (and erasure) also adds the normalized address to `contact_suppressions`, so re-adding the same person as a new lead (case or `+tag` variants included) is still refused. Phone/SMS withdrawals follow the lead id only: a re-added lead with the same phone number is NOT blocked (known gap; no phone suppression list exists).
- **It authorizes nothing.** A true answer is necessary, never sufficient, for outreach. FF Marketing stays dry-run (CHECK-constrained); `ffm_route_preview` now refuses a lead with no current consent.
- `evidence_ref` is a short pointer (form id, message id), screened like all `ffm_*` text. Not a place for conversations.
- **Limit: the bot can record consent.** `ffm_record_consent` is callable by the service role with any evidence pointer of 3+ characters; nothing verifies the evidence. A compromised or mistaken bot could record express consent.
- **What counts as implied consent, and for how long: OWNER/COUNSEL.** No number is chosen in code. Whether the lead sources used actually give lawful consent (CASL in Canada, and any other jurisdiction) is a legal question this log records but cannot answer.

## 4. Erasure
`ffm_erase_lead` (owner-only): records a withdrawal for all channels, redacts name/email/phone/source/note on the lead, blanks consent `evidence_ref`, overwrites the free-text `source` on the lead's consent rows with `[erased]`, and keeps the metadata rows (basis, channel, times, lead uuid) so withdrawals survive without personal data. Because client PII is not in the off-site file, erasure has no external copy to chase for client data. Copies in provider backups expire under the provider's retention.

## 5. Sensitive-data detector, health terms (decision B) and insurance product wording
`ws_sensitive_hits` gains a `health` category (20261119): a fail-closed screen with a long-stem substring list plus a short-word list with separator tolerance. **Limits (stated plainly):** regular-expression list, not a classifier. Misses misspellings, euphemisms and anything not listed. Refuses innocent text (listed false positives in `sqltests/ffm_consent_check.sql` section H; e.g. a substring can straddle a word boundary). It reduces accidental capture; it does not make health data lawful to hold, and no health data should be collected for FF Marketing at all. `ws_sensitive_hits` itself is unchanged by the insurance work below, so its own confirmed bypasses remain in that function (Cyrillic/Greek look-alike letters, accented forms such as `diábetes`, French such as `diabète`, leetspeak). The table guards no longer rely on it alone: they call the classifier in 5a, which closes those bypasses. The Python `screen()` pre-model check and `ffm_route_preview` still call the raw function; moving `screen()` to `classify_text(text, None)` (now available in `hq_workspace.py`) is a follow-up to do AFTER the migration is applied, because calling a missing RPC would fail.

### 5a. Insurance product marketing versus personal health information (20261122, default-deny; owner decision pending on the term, feature and vocabulary lists)
**Why.** The health detector refused ordinary insurance product wording ("health insurance", "disability insurance", "critical illness cover", "Medicine Hat"), so the insurance client (Client 2) could not write marketing. It also missed French, accented forms (`diabète`, `diábetes`), look-alike letters (Cyrillic/Greek homoglyphs), fullwidth letters and leetspeak. Both are addressed by `ws_classify_text(text, workspace)`, which `ws_guard` and `ffm_guard` now call.

**What the independent review found (PR #17, head d82e29a) and what changed.** The first design waived health wording with a DENY-LIST of personal words after an approved term was cut out. Review showed that once a product term was approved, personal health information passed in third-person wording whenever it avoided the word list ("Health insurance: client has lupus", "...client takes Lipitor", "Disability insurance: she broke her leg", Arabic/CJK/Devanagari text, splices like "dia health insurance betes"), that sensitive insurance application data was not detected at all without a health word ("Life insurance application for Jean Tremblay is pending underwriting"), that the owner could approve terms such as "cancer insurance" or place "Jean Tremblay", and that 19 of 91 legitimate sentences were refused ("Canada's #1 health insurance broker", "Health insurance @ $25/mo", "Income protection insurance"). The model is now **default-deny on the residual**: in insurance-related text everything that is not explicitly approved is refused.

**Second independent review (PR #17, head 0798846) and what changed again.** (1) Context was triggered only by insurance WORDS, so "Client has lupus", "Maria Gonzalez cannot walk", "Client takes Lipitor", "Our client has lupus" and foreign-language text (German, Turkish, Chinese, Arabic, Hindi, Italian, Spanish, Portuguese) were stored in an insurance workspace. Context is now a property of the WORKSPACE (`vertical = 'insurance'`, or any approved product term), not of the words. (2) The vocabulary held first-person plural words (we, us, our, nous, notre, nos) and generic person words (someone, one, ones, parents, people, children) that rebuilt personal sentences ("Life insurance: we need care", "...cancer in our family"); they are removed and hard-denied. (3) Vocabulary words that are also names ("Will", "Page", "Sam", "Summer") and place names that are given names (Victoria, Regina, Sydney, Brandon, Barrie, Vernon, Courtenay) passed ("Health insurance for Will Page", "Life insurance: Brandon"); numbers passed as age, years or a date ("age 54", "1985"), as spelled-out digit runs and as yes/no answers ("cancer: no"). (4) REGRESSION: a mortgage workspace refused "Mortgage rates - privacy policy", "Title insurance included" because any text with insurance or policy started the vocabulary test everywhere. (5) The owner hard-deny list could be bypassed by inflection or truncation ("lupuses", "lupu", "hivs") and lacked many conditions, drugs, relations and names.

**Third independent review (PR #17, head afc6c23) and what changed.** (1) Insurance ONBOARDING could not complete: `ffm_onboarding_items.value_text` (a CRM name and e-mail, a booking link, consent wording, "Jane Doe, compliance officer") got the marketing vocabulary test. Onboarding values now go through `ws_onboarding_value_check(template_key, value)`: every earlier category and the health screen with NO waiver, every word checked against the condition / drug / body / given-name lists (the words inside an e-mail or link included), no narrative or first-person context (consent wording may say "I agree"), no identifier; an e-mail address or link is accepted only for the business-contact keys (`crm_destination`, `booking_link`, `brand_assets`, `compliance_contact`, `ad_review_signoff`, `lead_fields_agreed`, `ad_account_access`, `consent_wording`), a phone number only for `compliance_contact`; a person name is refused everywhere except `compliance_contact`. The vocabulary test applies to MARKETING columns only (names, notes, headlines, bodies, CTA, audience note, ledger note). (2) The structural-column exemption stored personal text (`ffm_block_input(ws, key, 'Maria Gonzalez cannot walk, ODSP')`, a direct `UPDATE` of `title`, an `INSERT` of `approved_by`). `ws_structural_value(table, column, value)` now exempts a value from the vocabulary test only when it really is structural: `title` must EQUAL a template title, `blocked_until` must be a plain date ("Dec 1, 2026") or a short token, an enum / actor column (`status`, `stage`, `kind`, `provider`, `template_key`, `approved_by`, `provided_by`) must be a short token (letters, digits, `_ : . -`) or, for `approved_by`, an e-mail, and no word of it may be a name or a health word; anything else gets the full screen. (3) The yes/no rule is position- and punctuation-independent: a negation word (no, not, non, oui, yes, pas, none, never, nope) within any non-alphanumeric gap on EITHER side of an approved feature phrase refuses ("cancer? no", "(no)", ". No", "... no", "/ no", "| no", "No heart attack, stroke and cancer"); the feature marker is separate from the product marker so "Health insurance - no medical exam" is unaffected. (4) The "your income" waiver is refused when any English or French number word is present ("your income is fifty thousand", "votre revenu cent mille"). (5) Insurance scope is `vertical ~* 'insur|assur'` everywhere (insurance-broker, life insurance, insurance_brokerage, assurances, courtage assurance). (6) Fixed phrases and number forms (see below) cut the false positives; vocabulary grew by about 200 en/fr marketing words. (7) Spelled digit groups are counted across punctuation (4 or more number words anywhere in the text refuse); "can't / can not / cannot / cant / could not / unable to / won't ... work / walk / pay / afford / move / see / hear ..." and "needs care / surgery / treatment ..." refuse (generic-subject narrative: "Worker can not work", "Senior needs care", "Family can not pay bills"). (8) A vocabulary word that is also a given name is treated as a name BY POSITION: will / may / don / sam / bill / sun / sat / wed as the first or last word of the text, and will / may / don / sam / bill / page / mo / sun / sat / wed / summer / spring / mark / rose / grace right after for / to / of / from / beneficiary / named / by / with ("life insurance for will"). Seasons at the edge stay allowed ("Spring promo"). (9) The owner deny list gained the words the review listed (relations and nicknames, bereavement, blood / pressure / sugar / glucose, collapse, crutches, nursing, specialists, pill / dose, probate / estate, bankruptcy and debt words, custody / divorce, immigration words, jail / prison / felony / arrest, gambling, and the names sammy, jeanne, alissa, gonzales ...). (10) Item 11: the identifier-next-to-an-insurance-word screen that this migration had added for NON-insurance workspaces is REMOVED, so a mortgage workspace behaves exactly as before the migration (`jane@acme.ca about home insurance` is accepted there, as it was). That screen was new behaviour, not a safety property of the previous version; person tables keep the strict screen and an insurance workspace still refuses identifiers. (11) The classifier functions now pin `search_path = pg_catalog` and every reference is schema-qualified. (12) The exported schema (20261113) carries function source: the name and condition lists in this migration are stems or ROT13, and the sqltests assert that none of the exact fixture names PR #16's leak tests use (Vandenbroek, Prisca, Lachapelle, Theodore, Zalewski, Ximena, Zorro, Quenneville, Odalys, Brightwater, Tremblay, Plomberie, Zzyxwell, Quillfeather, Wexcombe, Bedard, Marcus, Eloise, Marie, diabetes) is readable in any `ws_*` / `ffm_*` function source. Generic condition words (lupus, cancer ...) remain readable in the detector functions by design.

**Owner-managed FIXED PHRASES (new list).** `ws_fixed_phrases` (en/fr, 2-5 plain words, owner-only `ws_add_fixed_phrase(lang, phrase)` / `ws_remove_fixed_phrase(id)`, soft removal, PII-free audit with ids and word counts, immutable and un-truncatable, RLS with service_role SELECT only). A phrase is cut from the token stream in pass 1 exactly like an approved term, so a word that is normally denied ("our", "us", "mon") is allowed INSIDE the phrase only. Seeded (en): contact us, call us, email us, text us, reach us, talk to us, our team, our advisors, our brokers, our experts, our guide, our free guide, our checklist, one call, one plan, one place, mon fri, mon to fri, plus about us, who we are, meet our team, our services / process / story / mission / partners / insurers / plans / products / offices / newsletter / blog / website, we can help, here to help, we are here to help, join us, visit us and similar; (fr): notre equipe, nos conseillers, nos courtiers, notre guide, contactez nous, appelez nous, joignez nous, lun ven, nos services, notre mission, nos partenaires ... "client", "I" and the first-person pronouns stay denied everywhere else ("our client", "we need care" still refuse). A phrase may not contain a person, narrative, claim or health word (the same hard deny list as the vocabulary).

**Number forms (round 3).** In addition to the earlier forms: "top N", "N reasons / raisons / stars / etoiles / steps / tips / questions", "over / more than / plus de N" (3+ digits, with space or comma thousands), "since / depuis YYYY", "N year / ans / years" immediately before an approved term and in "N year term", "N minutes / seconds", "December 25" (month + day), and times ("9am", "9 to 5", "9h a 17h") only next to an hours word or a Mon-Fri phrase. "Plan 1", "Option 2", a bare number and an age stay refused. Decorative symbols whitelist: the check mark, heavy check mark, ballot-box check, star (both), sparkles, right arrow, thumbs-up; every other symbol or emoji is refused.

**Model.** Insurance-related text may consist ONLY of (a) owner-approved terms, (b) words of an owner-managed generic marketing vocabulary, (c) numbers, prices, percentages and age ranges, (d) simple punctuation. Any other token is refused with the reason code `unknown_word` (the text is never echoed). The check runs on every free-text column of every non-person row **of an insurance workspace** (`client_workspaces.vertical` = insurance/assurance) **or of any workspace that holds an approved product term**, whatever the words are. In any other workspace (mortgage, ...) the vocabulary test does NOT run, so "Mortgage rates - privacy policy" and "Title insurance included" are accepted; there an insurance word only adds the identifier checks (phone, email, postal code, address, policy/claim number, date of birth), and a bare "policy" triggers nothing.

**Decision order** (`ws_classify_core`, reached through `ws_classify_text`; never echoes the text; returns `{"allowed": bool, "reasons": [codes]}`):
1. Every earlier category (SIN-like, card-like, account-like, identity document, banking, credit) is evaluated on the original text, a normalised view (zero-width/bidi characters, NFKC fullwidth/circled/squared/mathematical letters, accents and combining marks, `œ/æ/ß`, Cyrillic/Greek/Latin-extended look-alikes, Arabic-Indic digits) and two leetspeak views. Nothing here is waivable. Review fix: digits and symbols are folded into letters ONLY inside a token that contains a letter, so a lone `1`, `#1`, `|`, `@` or `$25` stands for itself. Policy/claim numbers and dates of birth are refused here too.
2. `health` and `income` (the only waivable categories): approved terms are cut out of the folded TOKEN STREAM (whole words, case/accent/hyphen insensitive, replaced by a marker, never re-joined), then the detectors run on what is left in all three views. "Your income"/"votre revenu" is waived only in insurance context and only when no currency amount appears (a product price like `from $25/month` does not count as an amount; `up to $4,500 a month` next to income does). Health wording left after the cut = `health:residual`; health wording and no term = `health:no_approved_term`.
3. In insurance context (workspace level, see above): identifiers (`identifier`), mixed Latin + Cyrillic/Greek letters (`mixed_script`), then the VOCABULARY TEST on the residual tokens (`ws_residual_check`): every token must be a vocabulary word, the cut-term marker, an allowed number FORM (see the table) or one of `. , ; : ! ? " ( ) / % $ | # + & @ -` in a harmless position; then capitalised names (`ws_capitalised_name`). Anything else, including emoji, non-ASCII letters (so every non-Latin script), `=`, attached `&`/`@`, percent-encoding, a bare number and a bare `150/95`, is refused.
4. Allowed reasons: `approved_product_term`, `approved_feature`, `approved_place`, `insurance_vocabulary`.

**Because the pieces around a cut term are tested one by one and never re-joined,** splices fail ("Health insurance for dia health insurance betes": `dia` and `betes` are unknown words).

**Where it applies.** Only on non-person tables: `ws_campaigns`, `ws_ledger`, `ffm_ad_sets`, `ffm_creatives`, `ffm_approvals`, `ffm_onboarding_items`. Context is decided per WORKSPACE (insurance vertical or any approved product term): every free-text column of the row gets the vocabulary test, so a split such as `name = "Health insurance"`, `note = "client has lupus"` is refused and so is `name = "Client has lupus"` on its own. Enum-like columns (`status`, `stage`, `kind`, `provider`, `template_key`, `approved_by`, an actor tag in `provided_by`, and for onboarding items the template `title` and `blocked_until`) skip only the vocabulary test, never the categories. Numeric columns are scanned by the categories only. The all-columns-joined scan keeps catching values split across columns (identifiers, health) without the vocabulary test. Person tables (`ws_leads`, `client_workspaces`, `ffm_routing_rules`, `ffm_consent_*`) keep the strict screen (plus the wider normalisation): a lead note "interested in health insurance" is still health information about a person. Practical consequence for onboarding values (`ffm_onboarding_items.value_text`): if a value mentions insurance it must be vocabulary-only, so write "Licensed agent, agency sign-off confirmed" rather than agency names next to the word insurance, or keep the detail in the client's own system.

**Owner-managed lists (all ship EMPTY except the vocabulary, which ships generic words only).** Rows are never deleted or edited; removal is a soft `removed_at`; every change is audit logged with ids and counts, never the text.
- `ws_approved_terms` (kinds `product`, `feature`, `place`) through `ws_add_approved_term(workspace, vertical, kind, term, confirm_vertical)` / `ws_remove_approved_term(id)`. OWNER-ONLY (the bot is refused). A vertical-wide approval needs `confirm_vertical = true` and is logged as vertical-wide.
  - **product**: 2-6 words, must name a product (insurance, assurance, coverage, protection, plan, policy ...). Every word must be marketing vocabulary or a product-name word (health, medical, dental, disability, critical, illness, accident, death, income, santé, invalidité, maladie, grave ...). So "cancer insurance", "diabetes coverage", "insurance for people with cancer", "hiv coverage", "insurance for her mother", "insurance for john smith", "Jean Tremblay insurance", "dr smith plan", "insurance for pregnant women" and "cover for seniors with dementia" are all refused (condition, person, name or targeting word). The word `income` is accepted only as a whole word in a product or feature phrase ("income protection", "disability income insurance").
  - **feature**: 2-12 words, a generic coverage description that may name conditions ("heart attack, stroke and cancer", "non smokers", "no medical exam"). Every word must be vocabulary, a product-name word, a companion word (attack, failure ...) or a word the health detectors recognise ONE BY ONE as a coverage subject; never a person, relation, narrative, claim or targeting word ("for people with ...", "his heart attack", "john smith heart attack" are refused). A feature phrase counts only next to an insurance word or an approved product term.
  - **place**: chosen from the fixed catalog `ws_place_catalog` (about 90 Canadian municipalities, changed only by a migration; municipality names that are also given names are left out). No free text, so a condition, a person or "Jean Tremblay" cannot be approved as a place.
- `ws_marketing_vocab` (per language en/fr, seeded with about 900 generic function and marketing words) through `ws_add_vocab_word(lang, word)` / `ws_remove_vocab_word(id)`: owner-only, one word of 2-30 letters, hard deny list in `ws_vocab_denied` (person references, relations and nicknames, titles, first-person and generic person pronouns (we, us, our, nous, notre, someone, one, parents, people, children ...), several hundred common en/fr given names and surnames, narrative words such as has/had/takes/took/was/lost/broke/diagnosed/is on, claim and underwriting wording, a long list of conditions, drugs and body parts, anything the health/condition detectors or any earlier category flag, `income`/`revenu`/`salary`). The check normalises first (case, accents, plural / -ed / -ing / final -e) and matches stems of 5+ letters as prefixes and 7+ letters anywhere, so inflections ("lupuses", "hivs", "lupusé") and truncations are caught. A word that is also a given name (Will, Page, Sam, Summer ...) cannot be added or used in a term. A denied word can never be added, by anyone.

**Round 4 (independent review RV17-C, PR #17): what changed, fail-closed.** All of it is asserted in `sqltests/insurance_classifier_check.sql` section R4 (expected in the comment, actual asserted).
- **Money, pay and debt (B1).** In an insurance workspace an amount of money is refused (`financial_detail`) unless it is one of two marketing forms: a PRICE PER PERIOD ("from $18 a month", "only $25/week", "dès 25 $ par mois", "$25/month": a lead word, at most 3 digits, per day / week / month; round 5: per month only) or a COVERAGE CEILING ("up to $500,000", "jusqu'à 1 000 000 $": the words and a round number of thousands; this one form is also exempt from the old seven-digit account-number rule, in an insurance workspace only). Refused whatever the other words are: every other amount ("$85,000", "45000 $", "85k", "$30/hour", a yearly price, a price list), spelled-out magnitudes (hundred, thousand, million, mille, cent; except a count such as "over ten thousand families"), a number word next to a period ("fifty a year"), spelled-out ages ("age forty five"), payment-trouble wording (late on, behind on, arrears, unemployed, bankrupt), and a pay / debt word (pay, paid, makes, earns, salary, paycheque, mortgage, loan, debt, tax, cash, rent, job ...) in the same value as any amount or number. The seed vocabulary no longer contains `late`, `losing`, `job`, `cash`.
- **Feature phrases (B2).** An approved feature phrase can no longer state a fact about a person. Any feature phrase is refused when it touches (over punctuation only) a second-person, possessive, family, having, negation, affirmation or answer word, or a check mark / star / arrow / thumb. A phrase that NAMES A CONDITION is accepted only as the whole value or inside a plain coverage template (product term, the phrase, and covers / coverage / protection / against / and / or / plus / including, fr couvre / couverture / contre / et / ou / y compris), and never in a ROW whose other columns hold such a word, a symbol, a digit or a number word ("you have" in the headline, the phrase in the body). On person tables feature phrases are never waived. The owner function now refuses a feature phrase that addresses, owns, counts, dates or negates ("you have ...", "no <condition>", "non smokers", "non fumeurs", "... free").
- **Which workspaces get the insurance screen (S3).** No longer a regular expression on the free-text `vertical`. Every workspace gets the insurance screen UNLESS its vertical is exactly `mortgage` (the only other vertical this system has a template for). NULL, blank, misspelled, new or unknown verticals and an unknown workspace id: insurance screen. A new non-insurance vertical is added by a migration (`ws_vertical_insurance`), never by naming a workspace.
- **Person tables (S2).** In an insurance workspace `ws_leads`, `client_workspaces`, `ffm_routing_rules`, `ffm_consent_log` and `ffm_consent_settings` now get the insurance screen column by column (`ws_person_column_check`), after the old screen: lead `note`, rule names and any other free text are default-deny vocabulary (no feature waiver); a lead `name` must look like a name (letters, at most 5 words, no health / relation / narrative / number / sentence word); e-mail and phone must have that shape; `source` is a tag of one or two plain words on no deny list; destination and evidence references are an e-mail, a link or a reference id (letters, then at most one group of up to 6 digits); a workspace name is list-screened. On UPDATE only the values that change get the insurance screen (an unchanged value keeps the old screen, so a stage change on a row stored earlier is not blocked by its old note); a row that moves into another workspace, or a workspace that changes vertical, is screened in full. Two things are never refused for wording: an erasure (`ffm_erase_lead` writes its own fixed values) and a WITHDRAWAL of consent (a source or evidence reference that passes the old screen but not the insurance screen is replaced by the fixed tag `withdrawal` / dropped, so the withdrawal is recorded and the text is not stored). A mortgage workspace is unchanged on every table (measured: 0 differences on 477 texts against the previous head, and the existing sqltests for it pass unmodified).
- **Also tightened.** Three number words in a row, and four across the columns of one row (S4). "<word> family", "famille <Name>", a closing "for <word>" and a Capitalised word after for / to / of / from / by / with / call / contact ... are read as a name (S5). One-word form labels with a colon (beneficiary:, age:, family:, exam: ...), a bare answer after a colon / question mark / dash ("exam: no"), a month and day outside a deadline ("policy date march 3"), age ranges narrower than 15 years (S6). Onboarding values: third-person and euphemistic wording, an insurer's decision, body measures, habits, amounts and pay wording (S7; the monthly budget may be an amount and nothing else). Vocabulary hard deny: aged, old, yes, weight, height, lbs, sober, expecting, shrink, owes, dui, earns, figures, applicant, smokes ... (S8). Actor tags: a pay / age / number token is free text (N5).

The same lines in a lead note of an insurance workspace: 132 before (old deny-list), **0 after**; as a lead source: 132 before, 4 after (one- or two-word misspellings and one French phrase on no list); as a lead name: 132 before, 5 after (2 real names, 3 one-word misspellings: a name column holds names). **Round 5 (independent review RV17-D and integration finding S7, PR #17): what changed.** Asserted in `sqltests/insurance_classifier_check.sql` section R5 (expected in the comment, actual asserted).
- **A withdrawal or an erasure is never refused for its wording (S4, safety).** A `ffm_consent_log` row with basis `withdrawn` (written only by `ffm_withdraw_consent` and `ffm_erase_lead`; the bot has no INSERT grant) is stored in EVERY workspace, mortgage included, whatever any column says. A column whose text fails the screen (the old screen or the insurance screen), a source longer than the 120-character column limit, or columns that fail only when joined, are replaced by fixed tags: source `withdrawal (wording not stored)` (a generated `via <channel>: ` / `no usable identifier for <channel>: ` prefix is kept), recorded_by `unknown (not stored)`, evidence_ref and wording_version NULL. The tag is the audit marker that wording was dropped. The withdrawal, its suppression entry and `ffm_can_contact = false` take effect. Consent RECORDING is not relaxed: a free-text actor or sensitive wording on `ffm_record_consent` is still refused (a refused consent can only reduce contact). The `erasure:<reason>` source is a literal of the erasure path only (withdrawn, all channels, by the owner); anywhere else it is screened (N5).
- **PR #20's consent columns (S7).** `verification` (the eleven codes `ffm_record_consent` sets), `basis` (incl. `unverified`), `channel` and the `[erased]` source are machine values: never screened, never joined. `evidence_ref` in PR #20's capture-reference shape (`^[A-Za-z0-9][A-Za-z0-9._-]{2,99}$`) skips the vocabulary test but every word still gets the name / health / pay / age / number checks and every earlier category applies ("diabetes form 2", "bank statement attached", `makes_85k`, `form-1984-03-12` stay refused). Key material, opted-out numbers, the outreach gate and restore markers live in tables that carry no guard; this migration does not attach one.
- **Money forms (B1, RV17-D).** ANY number next to a period word, in either order and with no currency sign needed ("85,000 a year", "6,500 monthly", "#850 weekly", "4,200 every two weeks", "plus de 85 000 par an", "annually: 85,000"); "over / more than / plus de N" unless it counts customers ("over 5,000 families"); a coverage ceiling followed by anything other than the end of the clause or a coverage word ("up to $85,000 a year", "up to $412,000 on the home"); a price per day or week (a price is now per MONTH only); a benefit / savings / budget / pension / retirement / receive word ("you get", "take home", "receives") next to any amount; payment trouble without an amount ("behind with the mortgage", "the mortgage is behind", "fell behind on rent", "missed two payments", "no savings", "a large loan", "makes less than", "a good living"); spelled-out ages ("forty five", "you are forty five", "quarante-cinq"); two ages ("ages 45 and 62"; an age range needs "to" / "-" and round bounds); and, across the columns of one row, a period word in one column with a money-sized number in another, or "your <pay / debt word>" next to any amount ("Your mortgage" + "From $999 a month"). Still accepted: "from $18 a month" (lead word, at most 3 digits) and a bare "up to $500,000" / "Coverage up to $1,000,000.".
- **Also.** Actor tags (`approved_by`, `provided_by`, `recorded_by`, `set_by`) with an insurer-decision, care, pregnancy, status or claim word, and any structural token that is a run of number words (`fortyfive`, `insurer_declined`, `needs_daily_care`, `expecting_wk20`) are free text (S6). Routing rule names may be a few fixed structural names ("Main rule", "Default route", "Backup CRM route", at most one digit), so they no longer need vocabulary words (N8). A lead e-mail in an import shape that `normalize_addr` accepts (`<a@b.ca>`, a trailing dot) is an e-mail address, not free text (integration with PR #20's re-import tests). The vertical comparison is documented exactly (N1): `lower()` and trimming of ASCII spaces only, then equal to `mortgage`; a tab, newline, non-breaking space, look-alike letter, fullwidth form, soft hyphen, `mortgages` or `mortgage-broker` is not `mortgage` (insurance screen).

(3) The split-column rules are coarse: a period word in one column and any money-sized number in another refuse the row ("Trusted by over 85,000 families" + "Review your coverage every year"), and "your paycheque / your mortgage" in one column with an amount, a percentage or a 3+ digit number in another refuses it. **Limits (stated plainly; asserted in `sqltests/insurance_classifier_check.sql` section L and the L lines of section R4).**
- Round 4 limits. (1) OVER-BLOCKING on independent copy is about two thirds: **83 of 127 held-out lines (65.4%)** are refused with the proposed terms, 92 (72.4%) as shipped; by kind: ads 23/40, emails 13/15, landing 9/20, social 15/15, French ads 9/18, French emails 5/7, French landing 4/7, French social 5/5. 45 of the 83 contain a hard-denied word (we / our / us / notre / nos 20 lines, people / clients / parents / person / someone / baby 10, pressure, rated, did, one, debt, income, health wording with no approved feature); 36 need only vocabulary the owner has not added (104 distinct words); 2 are number forms. (2) B1 over-blocks a price list ("$25, $40 or $60 per month"), a yearly or hourly price, any price next to a pay / debt word ("protect your paycheque from $25 a month") and spelled-out magnitudes ("one million reasons"). (3) B2 over-blocks a condition-naming feature phrase in the same value or row as you / your ("Get your free quote" as the CTA of that creative). "Non-smokers" / "non-fumeurs" can no longer be approved, so that copy is refused. (4) S5: in a text written In Title Case a capital letter says nothing, so "Call Day Today" passes; ordinary words Capitalised after for / to / with ... are refused. (5) S4: two number words per row repeated over several ROWS are stored (a row trigger cannot see other rows); integer columns are not screened. (6) S2: the lead name column holds names, so one to five words that are on no list are stored there; the source tag and the workspace name are list screens, not vocabulary tests; a lead note is vocabulary-only, so most free-text notes are refused (keep them in the client's CRM). "main" is refused in a reference id (French for hand). (7) S7: onboarding values remain a LIST screen: wording about a person that uses no listed word is stored; a licence number (`account_like_number`) and the licence class "accident & sickness" (`health`) stay refused. (8) S8: occupations are an open class and can still be added as vocabulary. (9) Emoji other than the short decorative list stay refused (many carry health meaning).
- Vocabulary-only text can still carry personal meaning: a vocabulary word that is also a first name used in a position the rule does not cover (for example "Brand on" for Brandon: a name split into two vocabulary words; a season such as "Summer" at the edge of a text, allowed on purpose because "Spring promo" is ordinary copy), up to three spelled-out numbers, and a feature phrase is generic only because the owner approved it ("Critical illness insurance for heart attack" passes once "heart attack" is an approved feature). Onboarding values are screened by lists, not by vocabulary, so a person name that is on no list (a single unlisted surname in `recruiting_model`, or in a booking URL) passes there; a single lowercase unlisted name used as an actor tag in `provided_by` / `approved_by` passes the token test. The test refuses what it does not know; it cannot know what a known word means in context. It is not a medical or legal classifier, and the owner and the client's compliance contact still approve every ad.
- Over-blocking is deliberate and MEASURED. Corpus `sqltests/data/insurance_marketing_corpus.txt` (205 natural en/fr marketing lines written independently of the vocabulary: headlines, bodies, CTAs, hours, social proof, product lines) was run in a workspace with 30 realistic product terms, 5 feature phrases and 6 places approved: **34 of 205 (16.6%) were refused at round 3** on this corpus, the author's own (it was 67% before the round-3 vocabulary, fixed phrases and number forms were fitted to it; the held-out figure is 65.4%, see the round 4 limits above; round 4 refuses a few more of these lines: non-smoker wording and a price list). Every remaining refusal, all of them fail-closed on purpose and listed here: (a) person words, which stay denied: "clients" x4, "customers", "people" x3, "parents", "key person insurance" x2 (the `person` word cannot be approved in a product name), "they", "we are proud" (the pronoun "we" exists only inside fixed phrases); (b) claim words ("claims" x3, "reclamation" x2); (c) personal life events and narrative: "getting married", "having a baby", "un bebe", "un mariage", "if you cannot work" x2, "if you are diagnosed", "illness or injury keeps you off work" (health wording with no approved term: the owner may approve the feature phrase); (d) deny-list words: "estate planning", "no pressure", "cote a cote" (`cote` is a surname); (e) owner approvals still needed: "Health and dental coverage" (approve it as a product), "without a medical exam" (approve it as a feature); (f) the rule limits: "more than 20 insurers" (the over / more-than form needs 3+ digits so that "over 65" stays refused), "retirement income" (the earlier income category), "est-elle" (third-person pronoun). Excluding the lines that are refused by design (a, b, c, d) the avoidable refusals are 6 of 205 (2.9%), of which 2 are cleared by owner approvals. Further words, phrases and number forms are added by the owner (`ws_add_vocab_word`, `ws_add_fixed_phrase`) or by a migration.
- Non-Latin scripts and German/Turkish/Spanish/Italian/Portuguese words are refused inside an insurance workspace (not vocabulary), and no term in another language can be approved in this version. In a NON-insurance workspace they get the previous screen only, plus the identifier checks next to an insurance word in a foreign language (versicher, seguro, assicura, sigorta roots).
- In a non-insurance workspace nothing new is refused at all (round 3); "Client has lupus" there is still accepted unless the previous health screen already refused it (it did not before either).
- Enum-like and actor columns skip the vocabulary test; a free-text `provided_by` other than an actor tag does not, and (round 4) neither does a token with a pay, age or number word (`makes_85k`, `age45`).
- Removing a term does not rewrite stored rows; the next UPDATE of such a row is checked again.
