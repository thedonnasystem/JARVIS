# Data classification, off-site backup and consent — policy as built

Status: ENGINEERING POLICY IMPLEMENTED IN CODE (dev branch, migrations NOT applied to production). Not legal advice. Items marked OWNER/COUNSEL are decisions this document does not make.
Owner decisions this implements (Nov 2026): A consent log, B health terms in the sensitive-data detector, C no client lead PII in off-site backups, D backups only after exclusions are verified.

## 1. What leaves the database, and what never does

| Class | Meaning | Off-site backup |
|---|---|---|
| `public` | non-personal reference data (e.g. published model prices) | exported |
| `internal` | the owner's and the ventures' operating data | exported |
| `client_pii` | third-party personal data: leads, prospects, replies, setters, suppression list, every `ws_*` and `ffm_*` table, `client_workspaces` | **never exported** |
| `secret` | push keys and endpoints | **never exported** |
| unclassified | a table nobody has classified yet | **not exported** (fail closed) until classified in a migration |

Decided by `public.backup_export_policy()` (table NAMES only, never data). Rules, in order of strength:
1. **Deny always wins.** `ws_*`, `ffm_*`, `client_workspaces` are denied by name pattern whatever any list says.
2. **Foreign-key closure.** A table with a foreign key to a non-exported table is not exported (a restore would otherwise load rows that point at missing data).
3. **Column drift.** A table on the allow side that gains a column that looks like personal contact data (email, phone, name, address, payee, birth…) and is not on the reviewed exception list (`backup_pii_column_exceptions()`) is excluded until reviewed.
4. **Second lock in code.** `hq_backup.py` re-checks every table against its own pattern (`ALWAYS_EXCLUDE`) and refuses to write a file if one gets through. It also refuses to run at all if the database function is missing or returns an unexpected result; there is no built-in "export everything" fallback.

The schema (structure, no rows) of every table, excluded ones included, is in the backup so a restore rebuilds the empty tables. The manifest lists what was excluded and why.

## 2. What this does NOT protect (read this before relying on it)
- **The live database and the database provider's own backups still contain client data.** This policy governs only the encrypted off-site file. Provider backups follow the provider's retention.
- **KNOWN LEAK PATHS (confirmed by independent review, NOT fixed in this PR).** The system itself copies client text into tables that ARE exported:
  - `record_lead_reply` / `mark_do_not_contact` put the reply note into `audit_log.detail.reason` (can contain a name, email, phone).
  - `setter_record_payout` writes the setter's real name into `ledger.note` (`setters` is `client_pii`, its name is exported anyway).
  - researcher/outreach output is stored in `tasks.result` (up to 8000 chars, includes prospect names, websites, published emails, outreach drafts); `agent_runs.summary` is free text.
  - Not fixed here because the functions are already live (applied migrations are not edited) and fixing them means redacting at source in a new migration or redacting at export, each with restore-fidelity consequences. **OWNER DECISION required before any backup key exists:** (a) redact these at source, (b) redact these fields at export (restore then loses them), or (c) accept them. The preflight fails until `BACKUP_LEAK_PATHS_ACCEPTED=1` is set deliberately. The drill's P1 check proves absence of the client TABLES only; it does not cover these paths.
- **Free-text in exported tables.** If a person types a lead's details into `memory`, `owner_messages`, `missions` or notes, that text is exported. The detector screens text written through the `ws_*` / `ffm_*` paths only.
- **Column-drift heuristic is best-effort.** It misses names such as `phonenumber`, `contact_name`, `surname`, `cell`, `telephone`, `street`, `postal_code`, `sin`, `msisdn`, `notes`, `recipient`, `customer`. The real control is that every table must be classified by a human in a migration.
- **Restore gap.** After a restore from an off-site file, every client table is EMPTY, including `contact_suppressions`. Before any outreach is ever enabled, the opt-out list must be restored from the provider backup. Never contact anyone from a restored database until that is done.
- **`BACKUP_KEY` / bucket policy** (rotation, who may read, retention) are OWNER decisions not made here. Backblaze is not activated and no key exists.
- Classification is a reviewed list. A mistake there (a client table labelled `internal` and with no suspicious column names) would be exported. The code lock in rule 4 covers the known client table names only. This is why a human review is required when a table is added.

## 3. Consent log (decision A)
- `ffm_consent_log` is append-only and immutable (trigger; `service_role` has no write grants). A withdrawal is a new row, never an update.
- `ffm_can_contact(lead, channel)` is default-deny. True only with a current express consent, or an implied consent inside an owner-set window (`ffm_set_implied_window`, owner-only; unset = implied consent not accepted). A withdrawal (channel or `all`), a suppression hit, a closed workspace, an unknown lead or channel give false. Withdrawal is final in v1. An email or `all` withdrawal (and erasure) also adds the normalized address to `contact_suppressions`, so re-adding the same person as a new lead (case or `+tag` variants included) is still refused. Phone/SMS withdrawals follow the lead id only: a re-added lead with the same phone number is NOT blocked (known gap; no phone suppression list exists).
- **It authorizes nothing.** A true answer is necessary, never sufficient, for outreach. FF Marketing stays dry-run (CHECK-constrained); `ffm_route_preview` now refuses a lead with no current consent.
- `evidence_ref` is a short pointer (form id, message id), screened like all `ffm_*` text. Not a place for conversations.
- **Limit: the bot can record consent.** `ffm_record_consent` is callable by the service role with any evidence pointer of 3+ characters; nothing verifies the evidence. A compromised or mistaken bot could record express consent.
- **What counts as implied consent, and for how long: OWNER/COUNSEL.** No number is chosen in code. Whether the lead sources used actually give lawful consent (CASL in Canada, and any other jurisdiction) is a legal question this log records but cannot answer.

## 4. Erasure
`ffm_erase_lead` (owner-only): records a withdrawal for all channels, redacts name/email/phone/source/note on the lead, blanks consent `evidence_ref`, overwrites the free-text `source` on the lead's consent rows with `[erased]`, and keeps the metadata rows (basis, channel, times, lead uuid) so withdrawals survive without personal data. Because client PII is not in the off-site file, erasure has no external copy to chase for client data. Copies in provider backups expire under the provider's retention.

## 5. Sensitive-data detector, health terms (decision B) and insurance product wording
`ws_sensitive_hits` gains a `health` category (20261119): a fail-closed screen with a long-stem substring list plus a short-word list with separator tolerance. **Limits (stated plainly):** regular-expression list, not a classifier. Misses misspellings, euphemisms and anything not listed. Refuses innocent text (listed false positives in `sqltests/ffm_consent_check.sql` section H; e.g. a substring can straddle a word boundary). It reduces accidental capture; it does not make health data lawful to hold, and no health data should be collected for FF Marketing at all. `ws_sensitive_hits` itself is unchanged by the insurance work below, so its own confirmed bypasses remain in that function (Cyrillic/Greek look-alike letters, accented forms such as `diábetes`, French such as `diabète`, leetspeak). The table guards no longer rely on it alone: they call the classifier in 5a, which closes those bypasses. The Python `screen()` pre-model check and `ffm_route_preview` still call the raw function; moving `screen()` to `classify_text(text, None)` (now available in `hq_workspace.py`) is a follow-up to do AFTER the migration is applied, because calling a missing RPC would fail.

### 5a. Insurance product marketing versus personal health information (20261122, owner decision pending on the term list)
**Why.** The health detector refused ordinary insurance product wording ("health insurance", "disability insurance", "critical illness cover", "Medicine Hat"), so the insurance client (Client 2) could not write marketing. It also missed French, accented forms (`diabète`, `diábetes`), look-alike letters (Cyrillic/Greek homoglyphs), fullwidth letters and leetspeak. Both are addressed by `ws_classify_text(text, workspace)`, which `ws_guard` and `ffm_guard` now call.

**Model.** Product marketing is permitted only as an EXACT, OWNER-APPROVED term with nothing personal around it. Everything else stays refused, and anything ambiguous is refused.
| | Handling |
|---|---|
| Approved insurance product names, general marketing copy, approved campaign descriptions (e.g. "Protect your family with health insurance", "Critical illness insurance from $25/month", "Assurance invalidité pour les travailleurs autonomes") | PERMITTED if the product phrase is an approved term (table `ws_approved_terms`) in that workspace/vertical and the rest passes the checks below |
| Personal medical information, health records, a person's disability or claim, sensitive insurance application information, SIN / passport / driver's licence / health card, banking, credit, income, card numbers, policy or claim numbers tied to a person, dates of birth, contact identifiers next to a health product phrase | REFUSED, always (fail closed) |
| Health wording with no approved term (the default; the table ships EMPTY) | REFUSED exactly as before |

**Decision order** (`ws_classify_text`, never echoes the text; returns `{"allowed": bool, "reasons": [codes]}`):
1. Every earlier category (SIN-like, card-like, account-like, identity document, banking, credit, application/income) is evaluated on the original text AND on a normalised view (zero-width/bidi characters removed, NFKC fullwidth, accents and combining marks removed, `œ/æ/ß`, Cyrillic/Greek/Latin-extended look-alikes mapped to Latin, Arabic-Indic digits) AND on two leetspeak views (`0 1 3 4 5 7 $ @ ! |` read as letters). A hit in any view refuses the text. Nothing here is waivable. Two new refusals sit in this step: an insurance identifier (`policy/claim/member/certificate/contract` followed by 5+ digits) and a date of birth next to a number.
2. Health wording (the old health list plus French and extra stems: `maladie`, `médecin`, `hôpital`, `invalidité`, `santé`, `cœur`, `chirurgie`, `enceinte`, `avc` and others) in any view. None found = allowed. Found and the workspace has no approved terms (or no workspace is given) = refused (`health:no_approved_term`).
3. Each approved term is matched EXACTLY (whole words; case, accent and hyphen/space insensitive) and cut out of the normalised text. If ANY health wording is left (a diagnosis, `diabetes`, `claim for my surgery`) the text is refused (`health:residual`). A term that is only part of a longer word does not match. Terms hidden by look-alikes or leetspeak do not match and the hidden word stays visible to the detector.
4. If a Latin letter is mixed with Cyrillic/Greek letters, the text is refused (`health:mixed_script`).
5. What is left must contain NO first-person or narrative context (`I`, `my`, `me`, `je`, `j'ai`, `ma`, `mon`, `mes`, `diagnosed`, `prescribed`, `suffers`, `atteinte`, `claim for`, `passed away`, `policy number`, `born`, `numéro de police` ...) (`health:personal_context`) and NO identifier (phone, email, postal code, street address, date, any 4+ digit run; prices like `$25/month` or `25$`, percentages, years 1900-2099 and age ranges like 18-65 are allowed) (`health:identifier`). Second person ("your family") and company voice ("we", "our") are not context.
6. Allowed with reason `approved_product_term` (or `approved_place`).

**Where the waiver applies.** Only on non-person tables: `ws_campaigns`, `ws_ledger`, `ffm_ad_sets`, `ffm_creatives`, `ffm_approvals`, `ffm_onboarding_items`. Person tables (`ws_leads`, `client_workspaces`, `ffm_routing_rules`, `ffm_consent_*`) keep the strict screen (plus the wider normalisation): a lead note "interested in health insurance" is still health information about a person. Columns are checked one by one AND joined, so an identifier in another column is caught.

**Approved terms.** Table `ws_approved_terms` (RLS on, service_role read-only, no row is ever deleted or edited; removal is a soft `removed_at`). Scope is ONE workspace or ONE vertical. `ws_add_approved_term(workspace, vertical, kind, term)` and `ws_remove_approved_term(id)` are OWNER-ONLY (the bot is refused), audit logged with the term id, kind and word count and never the term text. A term is 3-60 letters/spaces/hyphens/apostrophes (no digits or symbols, accents allowed), a product term is 2-6 words and must name a product (insurance, assurance, coverage, cover, protection, plan, benefit, policy, couverture, garantie ...), it must not contain first-person wording or anything the non-health categories refuse (income, banking, credit, ID), at most 100 active terms per scope. Kind `place` (e.g. `Medicine Hat`) is an explicit approved-place allow-list: it is the only safe way to fix "Medicine Hat"-style false positives, because the place is removed only when it matches exactly and the rest is still screened. Removing a term does not rewrite stored rows; the next UPDATE of such a row is checked again.

**Limits (stated plainly; asserted in `sqltests/insurance_classifier_check.sql` section L).** Regular expressions again, not a medical classifier. Known MISSES: abbreviations ("she has MS"), symptoms or conditions not on a list ("sugar problems", "fever"), look-alike characters outside the mapped Cyrillic/Greek/Latin-extended set (e.g. Armenian), health information given without any health word, and a person named next to a health product phrase with nothing else ("Health insurance for Marie Tremblay" passes: no health information is stated). Spaced-out letters are tolerated by the health stems but defeat the short-token detectors (`T4`, street addresses, `my`). Known OVER-BLOCKS (fail closed on purpose): `income` is never waived, so "disability income insurance", "income protection" and "protect your income" are refused; an amount of 7+ digits (`$1,000,000`) trips the account-number rule; unlisted health words ("medical exam", "healthy") need their own approved term or different wording; any `I`/`my` in the copy blocks a text that contains a health product phrase ("my family" included); a workspace NAME or lead record containing "health insurance" is refused (person/strict tables). Marketing copy is not a lawful basis: the owner and the client's compliance contact still approve every ad. No approval list is shipped; the AI must not choose one.

**Owner decisions needed.** (1) The list of approved product terms and places per workspace or vertical (a PROPOSAL is in `FFM_CLIENT2_INSURANCE_ONBOARDING.md`; nothing is enabled until the owner adds terms). (2) Whether `income`-bearing product names (disability income, income protection) should ever be waivable; today they are not. (3) Whether the strict person-table rule for lead notes stays as is (recommended).

## 6. Evidence this was verified (dev, scratch databases only)
- `scripts/backup_drill.sh`: real PostgREST-shaped calls against a scratch Postgres with the full migration set: encrypt, upload to a fake B2, restore with the read-only key, row-for-row compare. Check P1: no client table file in the archive and none of the seeded lead names, emails or phone numbers appear in any data file. Check P2: the manifest lists `leads` as excluded and the schema still rebuilds it. Restore reports client tables as "absent from backup, as required"; a client table present in a backup is reported as a policy violation.
- `sqltests/backup_exclude_check.sql`, `sqltests/ffm_consent_check.sql`, `test_hq_backup.py`, `test_restore_backup.py`.
- `sqltests/insurance_classifier_check.sql` (20261122): 74 allowed-text, 347 blocked-text and 33 refused-statement assertions (English, French, accents, look-alikes, fullwidth, zero-width, combining marks, spaced letters, leetspeak, mixed language, wrapped personal information, owner-only/audit/immutability, the table guards, asserted limits) plus a deterministic 2,500-text differential against the unchanged `ws_sensitive_hits` (2,017 texts with an old hit; with no approved terms none is ever allowed; no non-health category is ever waived; the 57 texts allowed despite an old health hit were each re-checked by an independent oracle; 2,121 blocked texts x 4 mutations never became allowed). `scripts/classifier_differential.py` runs the same invariants on a larger seeded corpus (`--n 20000`: see the PR for the run). `ops/rollback_insurance_classifier.sql` is exercised by `scripts/replica/run.sh` (twice, then everything re-applies).
- These are synthetic tests. They are not production proof; production proof requires applying the migrations under a separate release authorization and running the post-release checks.

## 7. Before any off-site backup is activated (all required)
1. Migrations `20261119_ffm_consent_v1` and `20261119_backup_exclude_client_pii_v1` applied to production under release authorization; `select public.backup_export_policy()` reviewed by the owner (every `exported` table is expected to hold no client data; `unclassified` should be empty).
2. Owner sets retention and who may hold `BACKUP_KEY`; key generated by the owner (`ops/generate_backup_key.html`), never by Claude.
3. Backblaze account, bucket and a write-only key (and a separate read-only restore key) created by the owner.
4. `ops/backup_activation_preflight.sh --require-pii-exclusion` passes (it reads `backup_export_policy()`; the known leak paths in section 2 need the owner's explicit decision), then one manual backup and one restore drill into a scratch database.

Rollback: `ops/rollback_ffm_consent_backup.sql` (drops the consent log — irreversible loss of consent history — and restores the previous functions; the old `backup_snapshot` exports client data, so no off-site backups while it is in effect).
