## 1. What leaves the database, and what never does

| Class | Meaning | Off-site backup |
|---|---|---|
| `public` | non-personal reference data (e.g. published model prices) | exported |
| `internal` | the owner's and the ventures' operating data | exported |
| `client_pii` | third-party personal data: leads, prospects, replies, setters, suppression list, every `ws_*` and `ffm_*` table, `client_workspaces` | **never exported** |
| `secret` | push keys and endpoints | **never exported** |
| unclassified | a table nobody has classified yet | **not exported** (fail closed) until classified in a migration |

Decided by `public.backup_export_policy()` (table NAMES only, never data). Rules, in order of strength:
1. **Deny always wins.** `ws_*`, `ffm_*`, `client_workspaces` are denied by name pattern whatever any list says.
2. **Foreign-key closure.** A table with a foreign key to a non-exported table is not exported (a restore would otherwise load rows that point at missing data).
3. **Column drift.** A table on the allow side that gains a column that looks like personal contact data (email, phone, name, address, payee, birth…) and is not on the reviewed exception list (`backup_pii_column_exceptions()`) is excluded until reviewed.
4. **Second lock in code.** `hq_backup.py` re-checks every table against its own pattern (`ALWAYS_EXCLUDE`) and refuses to write a file if one gets through. It also refuses to run at all if the database function is missing or returns an unexpected result; there is no built-in "export everything" fallback.

The schema (structure, no rows) of every table, excluded ones included, is in the backup so a restore rebuilds the empty tables. The manifest lists what was excluded and why.

That is still above the 60 s target only marginally and below the 120 s statement_timeout in this run, but the cost is now per audit field (about 1.3 ms) and not per character. The paged export of the same data: whole-export deny-list scan once (`backup_deny_prepare()`, **5.8 s**) then 500-row pages: **71.6 s of page time in 195 calls, worst single call 0.9 s**, plus the raw digests and the epoch reads (a few ms). Production today (303 audit rows, 183 tasks) is about 1-2 s. `hq_backup.py` asks `backup_snapshot_cost()`; the estimate was re-calibrated in round 5 (74 s estimated vs 67-72 s measured; it over-counts cheap fields on purpose) and the export is paged when the estimate exceeds **40 s**. Paging reads each table between two identical raw digests (`backup_table_digest`) and the whole export between two identical epoch vectors (rule 9). `scripts/perf_redaction.sh` measures the single statement (the replica gate runs it with a 60 s budget on 2,000 + 200: about 5 s).
    8. *Free text is blanked, not trusted to a regex (round 5, item E).* Columns that agents, scrapers, clients or counterparties write are exported as an empty string (JSON `null` for json/array columns) and listed in `manifest.redaction.blanked_columns`. **What is lost off-site:** the text of tasks (title, detail, result), agent run summaries, memory content, owner messages and answers, mission results/plans/evidence, escalation summaries/evidence, action log text, web messages, bank descriptions/payees, idea text, approval recommendations and the fetched evidence page text. Ids, statuses, amounts, timestamps, hashes and foreign keys are kept, so counts, money and the shape of the history restore exactly. **Restore:** `ops/restore_backup.py` turns every blanked column into NULL when the column is nullable, otherwise `''` (text), `{}` (jsonb object default), `[]` (array), so NOT NULL and CHECK constraints are not broken; the report counts them in `blanked_fields_restored_empty`. Rebuilding the lost text is a provider-backup restore, not an off-site one. The privacy rule wins over completeness: nothing was weakened to make backups more complete.
    9. *Consistency (round 5, items A and B).* A file is uploaded only if `manifest.consistency.consistent is True`; `false`, missing or unknown status is refused in `hq_backup.run()`, in `verify()` and by the restore tool (`--allow-unverified` exists for a disaster restore and is reported). The single-statement export is one database snapshot. The paged export (and the fallback) prove themselves with an **epoch vector** `backup_epoch()` read before the first page and after the last: one counter (a sequence bumped by owner-only statement triggers on insert, update, delete AND truncate of every redaction source: leads, setters, setter_events, setter_payouts, ws_*, client_workspaces, lead_replies, deals, contact_suppressions, and on the deny-list), a digest of the DISTINCT values of every redaction-source column (round 7: it replaces the row counts; it catches writes made with triggers disabled that change what the redaction reads, and ignores rows that add nothing), the deny-list row count, and md5 of EVERY function of the backup_* / redaction_* families plus the detector twin and the writer trigger (derived from the catalog by name, not a hand list) and of the full export spec (table list and every column's mode). Round 6: the bump is conditional (INSERT / DELETE only when a row was touched, UPDATE only when a redaction-source COLUMN of some row actually changed, via transition tables; 0-row statements, status / score / body updates and `on conflict do nothing` captures do not count; TRUNCATE always does), so continuous outreach writes to non-source columns cannot starve a paged backup; Round 7 (B2b): an INSERT or DELETE bumps only when it adds a NEW distinct value of a source column or removes the LAST row that holds one (a drafted outbox email to an already-known address, a NULL recipient, a duplicate lead row, a delete of one of two identical rows: no bump; more than 200 distinct values in one statement: bump). A new recipient or any source-column change still discards the archive and is retried (3 attempts). The code hash also covers each function's owner, ACL and COMMENT. Any difference discards the whole archive; the run retries up to 3 attempts, then fails: nothing is uploaded, the previous verified backup is untouched, the failure goes to `audit_log` and an owner message (once a day), and the next scheduled run retries. The fallback exporter is verified only by the same epoch (before == after, two identical reads); with the epoch function missing it refuses to upload. The sequence has no API privilege and `backup_epoch()` is service_role-executable but returns counters and hashes only.
    10. *Redaction cache (round 5, item C).* The paged export scans the live data once (`backup_deny_prepare()`) and pages reuse the result from `ffm_redaction_found`: an UNLOGGED table (so it is not in the WAL, nor in a physical backup of replicas), no API grant, excluded from the export by its `ffm_` name and by the policy, rows keyed by a random run uuid (`gen_random_uuid()`) bound to the caller (`role|session_user|jwt sub`). A page uses a row only for the matching caller, the matching run and a run younger than 20 minutes (binding: the caller is `role|session_user|jwt sub`, which through PostgREST is the same for every session of one role; the 122-bit run id is the real secret and can appear in PostgREST request logs, so since round 6 the stronger binding is that only the `backup_reader` identity can call prepare / release / page at all (rule 11); with the service key retained (rule 12 option C) another service_role session that learns a run id could release it, never read it); anything else (forged, another caller, expired, released) runs the whole scan, never skips it. `backup_deny_release(run)` deletes only that caller's run; `hq_backup.py` releases in a `finally` (success, failed page, exception). Rows older than the TTL are purged at every prepare and release, and by a pg_cron job (`ffm_redaction_found_purge`, every 15 minutes) when pg_cron exists; without pg_cron the per-call purge is the only cleanup and the documented scheduled task is: `select public.backup_deny_release();` hourly. ## 3. Consent log (decision A) and suppression
- `ffm_consent_log` is append-only and immutable (trigger; `service_role` has no write grants). A withdrawal is a new row, never an update.
- `ffm_can_contact(lead, channel)` is default-deny. True only if ALL hold: the outreach gate is open (section 8); the workspace is open; the lead has not withdrawn that channel or `all`; the lead's address (email) or number (sms, phone) is present, usable and not suppressed; and there is a VERIFIED express consent (section 4) or an implied consent inside an owner-set window (`ffm_set_implied_window`, owner-only; unset = implied consent not accepted). Every other path is false, including any error. Reasons are explicit (`suppression_unverified`, `withdrawn`, `suppressed`, `address_unusable`, `no_phone`, `phone_unusable`, `evidence_unverified`, `no_consent`, ...). Withdrawal is final in v1.
- **Email suppression** (`contact_suppressions`, append-only): an email or `all` withdrawal, and erasure, add the normalized address (case, `+tag`, trailing dot, `<>` forms collapse; non-ASCII or malformed addresses are refused as `address_unusable`), so a re-added duplicate lead is refused.
- **Phone suppression (new)** (`ffm_phone_suppressions`, append-only, same shape): a withdrawal on `sms`, `phone` or `all`, and erasure, add the lead's number normalized by `normalize_phone` to `+<digits>` (E.164-like): spaces, dots, dashes, parentheses, `+1` / `1` / `001` prefixes, trailing extensions, fullwidth and Arabic-Indic / Persian digits, zero-width and bidi marks are handled; a number with no `+` sign is treated as North American when it has 10 digits (or 11 starting with 1), anything ambiguous or with letters is unusable and therefore refused. A number-based withdrawal blocks every phone-based channel (sms and voice) - deliberately broader than the channel the person named. `ffm_can_contact` consults it for `sms` and `phone` (there is no separate `call` channel; an unknown channel is refused). **`mail` (post), `telegram`, `whatsapp`, `signal` and `other` are refused with reason `channel_prohibited` whatever consent is on record (section 9).** A re-imported or duplicate lead with the same number in any format stays refused. An email-only withdrawal does not suppress the number.
- **It authorizes nothing.** A true answer is necessary, never sufficient, for outreach. FF Marketing stays dry-run (CHECK-constrained); `ffm_route_preview` refuses a lead with no current consent (and so, while the gate is closed, every lead).
- `evidence_ref` is a short pointer (a capture reference, section 4), screened like all `ffm_*` text. Not a place for conversations.
- **What counts as implied consent, and for how long: OWNER/COUNSEL.** No number is chosen in code. Whether the lead sources used actually give lawful consent (CASL in Canada, and any other jurisdiction) is a legal question this log records but cannot answer.

## 4. Consent evidence (verifiable) and erasure
### 4.1 The evidence model
Problem fixed: until this change the bot's service role could record `express` consent by asserting any 3-character string as `evidence_ref`. Now:
- A **capture** (`ffm_consent_captures`, immutable) is a registered record: workspace, opaque `capture_ref` (the form-submission id; the pattern forbids spaces, names and addresses), channel, the approved **wording version and its sha256** (`ffm_consent_wordings`, registered by the owner), the sha256 of the stored raw artifact (the form submission as captured), the capture time, and a **keyed hash binding it to the contact** (or, for a hand-attested capture, to one lead id). The contact itself is never stored.
- Captures are written only by two paths the bot cannot use alone: **`ffm_ingest_capture`** (form ingest: the call must carry a *seal* = HMAC-SHA256 over the capture fields with the **capture signing key**; the key sits in `ffm_secrets` (no grant to any API role; no function returns it) and in the form endpoint, not in the bot, so the bot cannot produce a valid seal; `hq_consent.py` is the stdlib signer the form side uses) and **`ffm_register_capture_owner`** (owner-only; consent the owner personally attests, e.g. paper or a recorded phone call).
- `ffm_record_consent` records basis `express` **only** when `evidence_ref` names a registered capture whose channel, wording version and contact (or lead id) match. Anything else is stored as basis **`unverified`** (kept for the audit trail, with a reason code: `no_capture`, `channel_mismatch`, `wording_mismatch`, `contact_mismatch`, `lead_mismatch`, ...) and `ffm_can_contact` ignores it. `captured_at` of a verified consent comes from the capture, not from the caller. A CHECK constraint makes an `express` row without a `capture_id` impossible whatever function writes it. Implied consent is unchanged (owner-only).
- A capture does not validate another person, channel, wording or workspace (tested), and erasure blanks the contact hash on the person's captures.
### 4.2 What the database can and cannot know (and what a human must still do)
The database proves: this consent record matches a capture that was registered through the sealed form path or by the owner, for this wording, channel and contact. It cannot prove that the form really showed that wording to a real person who really agreed. **Owner/human still must:** generate and keep the capture signing key offline and give it only to the form endpoint (`ops/OWNER_CONSENT_INTEGRITY.sql`); register each approved wording with its hash; keep the raw artifact each `artifact_sha256` points to (the form submission with timestamp, wording and IP) in the client's or owner's system for the legal retention period; sample-check captures against artifacts; never use the owner-attested path to paper over a missing capture; decide re-opt-in (withdrawal is final in v1). The form-ingest endpoint does not exist yet; until it does, the only usable path is owner-attested, i.e. nothing is "express" without the owner. **Residual risks:** whoever holds the signing key (or the database owner, who can write anything) can mint captures; keys are visible in the SQL editor history when set (delete the snippet) and to the database provider; keys cannot be rotated in v1 (a rotation design is an owner decision).
### 4.3 Erasure
`ffm_erase_lead` (owner-only): records a withdrawal for all channels, adds the address and the number to the suppression lists, redacts name/email/phone/source/note on the lead, blanks consent `evidence_ref`, overwrites the free-text `source` on the lead's consent rows with `[erased]`, unlinks the person's captures (contact hash blanked, `erased_at` set), and keeps the metadata rows (basis, channel, times, lead uuid) so withdrawals survive without personal data. Because client PII is not in the off-site file, erasure has no external copy to chase for client data (the keyed suppression hashes are not reversible without the owner's key). Copies in provider backups expire under the provider's retention.

## 5. Sensitive-data detector, health terms (decision B)
`ws_sensitive_hits` gains a `health` category: a fail-closed screen with a long-stem substring list plus a short-word list with separator tolerance. **Limits (stated plainly):** regular-expression list, not a classifier. ## 8. Suppression survival, restore verification and the outreach gate
**Why:** `contact_suppressions` is client PII and stays out of the plain off-site file, but an opt-out list that vanishes on restore means a restored system would contact people who opted out.
**What travels (c):** `backup_suppression_export()` (called by `hq_backup`, additive, separate from `backup_snapshot`) returns only **keyed hashes**: `HMAC-SHA256(suppression key, 'sup|v1|' + length-prefixed kind + length-prefixed normalized value)` (email address or phone number), plus a count, a digest and a key fingerprint, written inside the encrypted archive as `suppression/hashes.json` and summarised in the manifest. The **suppression key** (`ffm_secrets`, set once by the owner via `ffm_set_key`) is a different secret from `BACKUP_KEY`, is never in any backup, and is kept offline by the owner. Without it a hash can neither be reversed nor tested against a guessed address, even by someone who has the file AND `BACKUP_KEY`. Not exported: addresses, numbers, keys, the capture registry, the gate state.
**Fail closed (backup run, Nov 16 2026):** `hq_backup` reaches the export through `_rpc` (the backup identity). If the export is refused (any HTTP error, e.g. 401/403 because the identity may not run it), missing (404, function not installed), unreachable, or not a valid keyed-hash export, the run FAILS: it records `backup_failed`, tells the owner, and uploads nothing, so no archive is ever written without the opt-out list by accident (`test_hq_backup.SuppressionSection`). The one exception is the database's own explicit answer that the owner has not set the suppression key yet: no list can exist then, so the backup is written with `suppression.included: false` in the manifest, the owner is told after every such run and `/backup check` warns, and a restore from it keeps outreach closed with no checkpoint (drill T6). Making that case fatal too is an owner decision (it would stop all off-site backups until the key is set).
**Identity (cross-PR dependency with PR #16 leak redaction):** PR #16 treats every `backup_*` function as backup-identity only (role `backup_reader`, `BACKUP_READER_JWT`) and revokes `service_role`. PR #16 round 8 adds `backup_suppression_export` (this exact name; do not rename it) to its `backup_reader` allow-list (13 functions). Until PR #16 is merged, `_rpc` in this branch is a stand-in that uses the service key and the migration grants `service_role`; after it, PR #16's `_rpc` (JWT only) is used and sqltests G7/G25 require that only `backup_reader` can run the export. The function's `search_path` is `pg_catalog` (PR #16 rule M17).
**What a restore does (d):** `ops/restore_backup.py` re-checks the list (sha256, count and digest recomputed independently; a removed, altered or undeclared entry refuses the restore), stages it in the restored database as the **expected checkpoint**, sets the **outreach gate to `unverified`**, requires the restored database to report the gate closed (else the restore FAILS), and prints the procedure. A backup without a section (no key set) restores with no checkpoint and the gate closed. The gate is also closed on a fresh database, on a missing gate row, a missing key, or after the live list shrank.
**The gate (default-deny):** `ffm_outreach_gate_open()` is true only when the gate row says `verified`, the suppression key exists, and the number of suppression rows has not dropped below the count at verification (the lists are append-only, so a drop means rows were removed under the triggers). `ffm_can_contact` / `ffm_contact_status` return false (`suppression_unverified`) while it is closed, and the legacy `outbox_dnc_guard` refuses to approve, send OR CLAIM an outbox row (a claim is the `sent_at` write `hq_mail` makes before the provider call; only releasing a claim is always allowed). One decision function, `outreach_recipient_problem`, serves the trigger and the RPC `outreach_send_allowed(outbox_id)` that `hq_mail._claim`/`deliver_approved` call before the claim and again immediately before the provider POST and that `hq_venture_ops.dnc_problem` calls at approval; every Python caller fails closed on any error, timeout or answer other than `{"allowed": true}`. It covers the gate, the lead flag, email via `is_suppressed` (plaintext AND hash-only) and phone numbers for the text/call channels (plaintext AND hash-only; an unusable number is refused). Drafts are still allowed; they contact nobody. Anyone (the bot included) may CLOSE the gate (`ffm_close_outreach_gate`); only the owner-only `ffm_verify_suppression` can open it, and only if **every** entry of the staged checkpoint is present in the live list (plaintext lists plus imported hashes; extra live entries are fine), the key matches the checkpoint's fingerprint, and the staged checkpoint itself was not altered after staging.
**Owner procedure after a restore** (also printed by the tool): 1) no outreach; 2) `ffm_set_key('suppression_hmac_key', <the offline key>)`; 3) re-establish the list: provider backup rows (best: it has the addresses) and/or `ffm_import_suppression_hashes()` (hash-only entries are honoured by `is_suppressed` and `ffm_can_contact`); 4) `ffm_verify_suppression('owner')`; 5) if it says `incomplete`, `key differs` or `altered`, or the backup has no checkpoint: stay closed and rebuild from the **provider backup** (Supabase daily backup / PITR if the plan has it; the owner confirms what the plan provides) or from the unsubscribe and reply history.
**After ANY restore, including a provider restore (PITR, full `pg_dump`, a Supabase backup restore): the gate now closes itself (section 10); closing it by hand first is still the right reflex and costs nothing, but nothing relies on it.** The gate row is ordinary data. A provider restore brings back a gate row that says `verified` from the moment of the snapshot, with the gate OPEN, while every suppression added after that snapshot is gone, and nothing notices. So the owner runs `select public.ffm_close_outreach_gate('provider restore', 'owner');` immediately after, re-establishes the list (provider backup rows of a LATER point if the plan has them, the unsubscribe/reply history, the off-site hashes), and only then verifies against an **independent** source: a checkpoint taken from the audit-log record of the last export, or the file hash recorded outside the database (`--expect-sha256`). `ops/OWNER_CONSENT_INTEGRITY.sql` step 6 and `BACKUP_RECOVERY.md` carry the same instruction.
**What verification really protects (read this):** `ffm_import_suppression_hashes()` followed by `ffm_verify_suppression()` is circular: the imported hashes ARE the checkpoint, so it always says verified. It proves only that the import happened. The protection comes from the checkpoint being trustworthy, i.e. matched to something the restoring database and the bot cannot have written: `ops/restore_backup.py` therefore REQUIRES `--expect-sha256` (the file hash from the audit log or your own records); without it you must pass `--i-accept-unverified-suppression`, which makes the tool IGNORE the checkpoint in the file (nothing is staged, the gate stays closed) and the owner stages a checkpoint from an independent source. A restored schema with no outreach gate at all FAILS the restore.
**Keys and query logs:** `ffm_set_key` receives the key as a SQL argument, so the statement text can land in a database query log (`log_statement`, slow-query logs, and the error log if the call fails). Mitigations: check the key locally first (`CONSENT_KEY_CANDIDATE=... python3 hq_consent.py check-key`, prints only a verdict) so the call does not fail; use the psql variant in `ops/OWNER_CONSENT_INTEGRITY.sql` (key read from a file on tmpfs, never typed, never in shell history, `\unset` afterwards); confirm `show log_statement;` is `none` or `ddl` for the session; never paste a key in chat or a ticket; treat any key that appeared in a log as burned (rotation is a new design and an owner decision in v1). The refusal messages, the audit log and the return value never contain the key.
**`app_owners` (finding 3):** `is_app_owner()` trusts the `app_owners` table, and in production `service_role` held every privilege on it (read-only check, Nov 15 2026: `service_role` ALL, `anon`/`authenticated` none, RLS on, no policy, no trigger), so a holder of the service key could add an owner. No repository code writes it (owners are added by hand in the SQL editor, which runs as `postgres`); the bot only reads it for the backup. Migration `20261121_suppression_integrity_v1` section 13 revokes insert/update/delete/truncate/references/trigger from `service_role`, `anon` and `authenticated` and keeps `select`. Assumption to keep true: nothing that runs as `service_role` may ever need to write `app_owners`; add owners from the SQL editor.
**Limits and residual risks (stated plainly):** (1) a self-consistent but SMALLER hash list swapped into the file is detected only if the owner passes `--expect-sha256` taken from the owner's own records (a password manager entry or a note written when the export was made), NOT from `audit_log`: `service_role` can write `audit_log`, so a hash read from it is no independent checkpoint (the drill proves both outcomes; without it the tool now ignores the file's checkpoint); the DB cannot know a checkpoint is too small. (2) Verification proves the live list contains the checkpoint, not that the checkpoint contains everyone who ever opted out; opt-outs made after the last backup exist only in the provider backup. (3) Keys cannot be rotated in v1; losing the suppression key makes backup hashes useless. (4) A database superuser can edit anything, including the gate; the gate defends against the bot, bugs and restores, not against a malicious database owner. (5) The shrink check is a row count, not a content check; `ffm_verify_suppression` is the content check and should be re-run after any incident. (6) Legacy `leads`/`outbox` suppression (`contact_suppressions`) of the older venture outreach path is covered by the same list and gate. (7) FIXED in review (finding 1): `ffm_suppression_mac(kind, value)` was callable by the bot and, because `kind` was free text and both keys could be set to the same value, it was an HMAC oracle that could forge a capture seal. Now: every HMAC message is domain-separated (`cap|v1|`, `sup|v1|`, `con|v1|`, `key|v1|`) with length-prefixed fields (so no string can be re-split), the function no longer exists (the hash is computed inline inside the SECURITY DEFINER lookups, so no role can call a signing/hashing function over the stored keys), `ffm_set_key` refuses weak, repeated-pattern, equal, containing or overlapping keys (`ffm_key_problem`, mirrored by `hq_consent.key_problem`), and `capture_ref` may not contain `:` or `|`. `sqltests/consent_review_fixes_check.sql` replays the reviewer's attack with identical and with distinct keys. Why a revoke was not enough: the lockdown migration grants execute on every public function to `service_role` and is re-run last, so a revoke would silently be undone. (8) Classification of the new tables is by the `ffm_*` NAME rule on purpose, so a later replacement of `backup_classification()` cannot re-expose them (`sqltests/consent_integrity_check.sql` G13-G15 assert it).

## 10. Restore-closed gate: a restored database must close itself (v3)
**Problem:** the gate row, the suppression lists, the checkpoint and any counter live in the SAME database. A provider restore returns a self-consistent older copy: gate `verified` (OPEN), an old checkpoint, a shorter list. Nothing inside the copy can tell, and the previous design relied on the owner remembering to close the gate.
**Mechanism (all of it must hold for the gate to be open; `ffm_outreach_gate_open()`):**
1. verified by the owner (`ffm_verify_suppression`), key present, list not shrunk (as before);
2. **suppression epoch**: `ffm_epoch` is a monotonic counter bumped by every write to a suppression list, the consent log, the lead do-not-contact flag and every gate transition (an update that lowers it is refused). The gate records the epoch at verification and the database epoch must still be at least that;
3. **instance fingerprint** `system_identifier:timeline:database oid:gate-table oid`: recorded at verification; a dump restored into another cluster has another system identifier, a point-in-time recovery promotes a new timeline, and a logical restore (`pg_restore` into a new database, or into this one after `--clean`) creates the database and the tables afresh with NEW OIDs, so the stored fingerprint no longer matches (the same-cluster logical restore is therefore closed by the database alone; `backup_drill.py` V5 restores for real) (readable by the production `postgres` role: read-only check Nov 15 2026; if it were ever unreadable the value is `unavailable` and this layer is absent, nothing else changes);
4. **restore marker**: `ffm_restore_markers` (append-only). The OWNER records one with `ffm_owner_record_restore()` (owner only: the old anyone-callable `ffm_record_restore` is gone, because the lockdown migration grants execute on every public function to `service_role`), `ops/restore_backup.py` writes one, and the sender writes a `detected_by_sender` marker when it sees a rollback (that one never authorises an anchor). The decision is **deterministic, with no wall-clock comparison**: the verification stores `verified_marker_id` (the newest marker id at that moment) and the gate is open only while that is STILL the newest id. A marker recorded later, a marker with a clock of any year, or a marker table rolled back all close it; re-verifying always re-opens it at once (no sleeps, no race);
5. **sender attestation, minutes**: the gate is open only if `attested_at` is within `attest_window_minutes` (default 15, owner-settable **6-120**: the engine tick is **300 s** (`bot.py`: `run_repeating(hq_engine.tick, interval=300)`), so the window must exceed two ticks or the gate would flap on a missed tick). **Residual after the OID fingerprint (review F1, stated plainly):** a DATA-ONLY or in-place restore that keeps the database and table OIDs, and a physical restore that keeps the timeline, still bring back an old, self-consistent, freshly attested gate; the database alone cannot tell until the sender next attests (the next tick, up to 300 s, or the next email send, which attests first). Two consequences are enforced: (1) the owner approval path `hq_venture_ops.dnc_problem` now calls `hq_gatemark.attest(force=True)` BEFORE asking the database, and refuses unless the sender's outside mark vouches for it (tested); (2) **text and call (sms/phone) are DISABLED at the database by default** (`ffm_gate_config.phone_outreach_enabled = false`; owner-only `ffm_set_phone_outreach`, which also closes the gate), because no sender attests for them: every drafting, approval, claim and decision path answers `channel_disabled` (tests P1-P6). **OWNER DECISION G7:** enabling text/call is only safe once a sender for those channels attests against the outside mark the way `hq_mail` does; until then keep them off. Email delivery never relies on the window. **Window bounds:** at most 15 minutes (default) of exposure for a restored copy when no sender runs, at least 6; for a restore taken inside the window the sender's first attestation (the next tick, up to 300 s, or the next send, which attests first) closes it, so the practical worst case is one tick, not the whole window. The owner's verification is a first attestation; afterwards only the SENDER keeps it fresh by calling `ffm_sender_attest(generation, epoch, instance)` on every engine tick and before every send. **The database claim guard requires a fresh attestation:** `outreach_recipient_problem`, `outbox_dnc_guard` and `outreach_send_allowed` all call `ffm_outreach_gate_open()`, which is false once `attested_at` is older than the window, so a claim with no live sender is refused by the database itself (tested: consent_restore_gate_check R3b/R3c and the claim-guard cases in consent_integrity_check). A restored copy carries an old `attested_at`, so with no sender it closes by itself;
6. **maximum age, days**: owner verification older than `max_verified_age_days` (default 30, owner-settable 1-90) closes the gate; the owner re-verifies (`ffm_verify_suppression`).
**The sender's outside high-water mark (`hq_gatemark.py`):** the sender keeps the highest `(generation, epoch)` it has seen OUTSIDE the database and passes it with every attestation. If the database epoch is lower, or the instance differs, the database closes its own gate for good (marker + close, in the database, not only a refusal in Python) and `hq_mail` sends nothing. No mark at all means UNANCHORED: the sender refuses and never anchors itself to a database; only the owner can anchor (`/gate anchor`), and **an anchor can never lower the mark after an undetected provider restore**: it needs the gate freshly verified after the newest marker (`ffm_gate_core_ok`), and, if the database epoch is below the mark, an OWNER restore marker newer than the one the mark last consumed (the mark file records it, `om`). The database enforces the same rule against its own stored mark (`ffm_sender_mark`, monotonic: a lower mark is refused with `mark_regression` and refreshes nothing; a higher generation needs an unconsumed owner marker; the anchor must carry exactly the current epoch). **The only way down is: owner-recorded restore, then verify, then anchor, in that order** (`ops/OWNER_RESTORE_RUNBOOK.md`; `/gate` prints the next required step). A configured store that cannot be read, or none configured, is a refusal. Where the mark lives, with no new paid service and no new secret: (a) one object per advance in the existing Backblaze B2 backup bucket under `<prefix>gate/`, the mark carried in the FILE NAME (`hwm-<gen>-<epoch>-<owner marker>-<fingerprint>.json`, matched with `fullmatch` against the exact prefix) so no read permission is needed, same `BACKUP_PUT_URL`/`BACKUP_AUTH`. **True B2 capability (Backblaze docs, Application Key Capabilities, checked Nov 15 2026):** `writeFiles` covers `b2_upload_file` AND `b2_hide_file`; `deleteFiles` covers `b2_delete_file_version`. So a key with only `listFiles` + `writeFiles` CAN hide a mark object and CAN upload another version of the same name, but CANNOT delete a version. This is not append-only in the strict sense, so the sender reads with `b2_list_file_versions` (hidden uploads are still listed there), takes the maximum over every upload version, and COUNTS hide markers and foreign objects (`/gate` warns). Hiding therefore cannot lower the mark; what a stolen key could do is add a bogus HIGH mark (a denial of service: the sender then refuses until the owner re-anchors). Never give this key `deleteFiles`, and keep any bucket lifecycle rule (e.g. delete hidden versions after N days) OFF the `gate/` prefix; (b) optionally an append-only file (`GATE_HWM_FILE`, useful on a Railway volume). The effective mark is the highest found in ANY configured store.
**`ops/restore_backup.py`:** the restore, the restore marker, the recreated epoch row (value 1, below any sender mark) and the closed gate commit in ONE transaction (no committed moment with data and no marker); a schema without the marker/epoch tables FAILS the restore.
**Options evaluated:**
| Option | Verdict |
|---|---|
| Sender mark in B2 append-only objects + local file (chosen) | needs no new infra or secret; survives a database restore; detects any rollback that does not also reset the sender's stores |
| Mark in a Railway environment variable | rejected: writing a variable needs a Railway API token in the bot (deploy-capable secret) and triggers a redeploy |
| Railway container disk only | accepted only as a secondary store: wiped on redeploy, which yields UNANCHORED (safe), not trust |
| Telegram message to the owner as the store | rejected: bots cannot read history back |
| Second database / edge function / GitHub as the store | rejected: new paid infra or a new credential |
| `pg_postmaster_start_time`, sequences, `txid`/`xmin` | rejected: sequences and txids roll back with the data; postmaster time changes on every restart (constant false alarms) and not on a logical restore. The timeline id is what a PITR changes, and is used |
| Short TTL alone | used (5, 6) but insufficient alone: a snapshot younger than the window is still open |
| Epoch + restore marker without a sender | insufficient: a provider restore writes no marker |
**What is verified (scratch Postgres 16, `sqltests/consent_restore_gate_check.sql`, `scripts/backup_drill.py` V1-V9, `test_hq_gatemark.py`, `test_restore_backup.py`):** old gate OPEN + old checkpoint restored together with the late opt-out missing; provider-level restore (`pg_dump` into a new database, no tool of ours); restore without verified suppression state; restore into ANOTHER REAL CLUSTER (second server, different system identifier); restore with no sender running (closes after the window); unanchored sender; mark never moves down; re-anchor starts a new generation; epoch row missing; fingerprint missing; verification older than the limit; marker newer than the verification; B2 listing format and paging against a fake of the B2 API.
**WHAT REMAINS (stated plainly):**
- **Exposure window.** A provider restore to a point younger than the attestation window shows the old gate OPEN and the lost opt-outs not suppressed until the first sender attestation (the engine tick, about a minute) or until the window ends if no sender runs. The drill asserts this (V5) so the document cannot drift. Shorten the window (minimum 6 minutes) if that is too long.
- **Not detectable by the mark:** a restore that ALSO resets every store the sender uses (the B2 gate objects deleted or rolled back, the file gone) followed by an owner anchor. The owner's record-verify-anchor sequence is then the only barrier (the database's stored mark is rolled back too in that case, so the DB-side anchor rule cannot help; the checkpoint verification can). After a provider restore record it explicitly with `ffm_owner_record_restore` from the SQL editor. Opt-outs recorded after the sender's last observation and lost together with a restore to a point after that observation are not detected (the tick and `observe()` after each unsubscribe keep that window to about one tick).
- A database superuser (and the service key for what it can write) can edit anything, including the epoch and the gate; this defends against restores, bugs and the bot's normal permissions, not against a hostile owner of the database.
- A failover or Supabase compute change that alters the timeline closes the gate (false positive, safe): re-verify and `/gate anchor`.
- Epoch and markers are ordinary data and are restored with the database; that is why the comparison value is held outside it.
- Not tested live: real Backblaze (only the API shapes against a fake), a real Supabase PITR, the `pg_control_*` read on the production role beyond the read-only SELECT above.
**Owner cost:** at setup, verify the list (already required) then send `/gate anchor` once; after a real restore, redo the verification and `/gate anchor`; every 30 days (or the value you set) re-run `ffm_verify_suppression`. If any of that is skipped the gate stays closed: the failure direction is "no outreach".

### 10.1 Service-key powers (what the bot's key can and cannot do to the gate)
`lockdown_v1` re-grants execute on every public function to `service_role`, so a revoke-only fix does not hold; each function is safe by its body. Assessed and tested post-lockdown with hostile arguments (`consent_restore_gate_check.sql` section S):
| Function | Bot-callable | Assessment |
|---|---|---|
| `ffm_epoch_bump_now` | REMOVED | the epoch is bumped only inside the trigger functions (inlined update); `ffm_epoch_bump`, `ffm_epoch_guard`, `ffm_lead_identifier_guard` are trigger functions and cannot be called |
| `ffm_record_restore` | REMOVED, replaced by `ffm_owner_record_restore` | owner-only (`ffm_require_owner`); a bot-written marker could close the gate for good (denial of service) or consume nothing, and an anyone-callable one blurred the owner/sender distinction |
| `ffm_close_outreach_gate` | yes, kept | it only REDUCES what is allowed (fail-closed) and the sender needs it to close on suspicion; a hostile caller can stop outreach (denial of service, audited, the owner re-verifies) but cannot open or lower anything |
| `ffm_sender_attest` | yes | monotonic against the DB-stored mark: a lower mark is refused and refreshes nothing; it refreshes `attested_at` only when the mark is not below the stored one and the gate core is valid; it cannot open a closed gate; a higher generation needs the owner marker; a mark above the database epoch closes the gate (denial of service only). Residual: a stolen key can keep a STALE-but-verified gate fresh by presenting the stored mark; that is the limit of any check the key holder can answer, and why the mark lives outside the database |
| `ffm_verify_suppression`, `ffm_set_gate_config`, `ffm_owner_record_restore` | refused for the bot | owner-only |
The ACL manifest `ops/ACL_MANIFEST_public.tsv` now covers EVERY function, table, view and sequence in schema public per role (generated by `scripts/acl_manifest.py` from the catalog after all migrations; `--check` is part of the gate's manifest step, so any drift fails it). One tab-separated row per object (`kind, name, anon, authenticated, service_role, security, note`), sorted, so it merges with another manifest by concatenation and `sort -u`; the same columns are to be used by the post-lockdown ACL manifest on `build/leak-redaction`. anon/authenticated holding anything on a function or on a consent-integrity table fails the generator.

### 10.2 Cost and bounds
Epoch hot row (scratch Postgres 16, this machine, `ffm_epoch` is one row updated by a statement-level trigger): a 1000-row bulk INSERT into `contact_suppressions` is ONE statement and ONE bump (22 ms); 1000 single-row INSERTs in one transaction 159 ms against 117 ms with the trigger off; concurrent single-row autocommit inserts serialise on the row: about 900-1000 transactions/s at 1, 8 and 32 clients (against 1900 and 4150/s at 8 and 32 clients without the trigger). Suppression writes are human-rate (unsubscribes), so the ceiling is irrelevant for them; do not put the epoch trigger on a high-rate table. A 1000-row lead import costs about 1 s more with the identifier trigger (10.2 s against 9.1 s; the rest is existing triggers). Transient fingerprint read failures are retried inside `ffm_instance_fp` (3 tries); a persistent `unavailable` closes the gate and writes NO marker and no owner action is requested, the sender call returns `instance_unreadable`.

### 10.4 Limits recorded from the independent verification (RV20-B)
- **N1 (service-key honesty):** a caller holding the service key can re-open a RESTORED stale gate in one call by reading `ffm_gate_state` and presenting the stored mark to `ffm_sender_attest` (only while `core_ok` holds: same instance and timeline, no later marker, under 30 days). The outside mark is only as honest as its caller; this defends against restores and bugs, not a hostile service key. A restore to a snapshot older than the first anchor has `ffm_sender_mark.gen = 0`, which re-enables the first-setup anchor path without an owner marker (it still needs `core_ok` and the exact current epoch). With the OID fingerprint a logical restore is not `core_ok` at all.
- **N4 (B2 growth):** one mark object per observed epoch advance, no delete permission by design, and the reader gives up after 100 pages of 1000 versions (`B2 listing did not finish`, permanent fail-closed). Years away at human-rate suppression writes. **Retire path:** the owner, in the Backblaze console (a key with `deleteFiles`, used only for this), deletes all but the newest generation's objects under `gate/` (never the highest), then runs `/gate` to confirm the mark is intact. Do not give the bot's key `deleteFiles`.
- **Gmail dot aliases (N5):** the email normaliser lowercases, strips `+tag`, display names and trailing dots, but does NOT remove dots in the local part: `j.doe@gmail.com` and `jdoe@gmail.com` are separate entries although Gmail delivers both to one mailbox. Fails OPEN in the direction of a Gmail dot alias. A provider-specific rule (Gmail only) was considered and rejected for now: dot-stripping is wrong for most other providers and, applied to the suppression list, would silently suppress distinct people. Recorded as a limitation; a person who opted out under one dot form can be contacted under another.
- **Fingerprint after a fast-promoted PITR (N5):** `pg_control_checkpoint().timeline_id` may still show the old timeline until the end-of-recovery checkpoint completes. Theoretical and NOT tested (no real PITR available here); the sender's mark and the stale-attestation window are the backstops.
- `is_suppressed` and `ffm_is_phone_suppressed` now return TRUE (fail closed) when hash-only entries exist and the suppression key is missing (tested R10g).
- A lead INSERTED already flagged do-not-contact now moves the epoch (row trigger `ffm_epoch_bump_ins`, tested R1f). `outbox_dnc_guard` refuses the consent log's names `sms` / `phone` as outbox channels explicitly (`invalid_outbox_channel`), not through the CHECK constraint.

### 10.3 Phone numbers without a country code
Documented and tested: a bare 10-digit number (any punctuation) is read as `+1` (Canada/US, NANP, the only region the owner contacts today); `6135550150` and `+16135550150` are the same number for suppression. Any other bare length (7, 9, 11 digits not starting with 1, UK trunk-zero national forms) is refused as `phone_unusable` and can never be allowed. If other regions are contacted later, the default must be changed in a reviewed migration.
