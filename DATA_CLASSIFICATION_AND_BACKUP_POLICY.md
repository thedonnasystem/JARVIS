# Data classification, off-site backup and consent — policy as built

Status: ENGINEERING POLICY IMPLEMENTED IN CODE (dev branch, migrations NOT applied to production; leak-path redaction added Nov 15 2026). Not legal advice. Items marked OWNER/COUNSEL are decisions this document does not make.
Owner decisions this implements (Nov 2026): A consent log, B health terms in the sensitive-data detector, C no client lead PII in off-site backups, D backups only after exclusions are verified.

## 1. What leaves the database, and what never does

| Class | Meaning | Off-site backup |
|---|---|---|
| `public` | non-personal reference data (e.g. published model prices) | exported |
| `internal` | the owner's and the ventures' operating data | exported |
| `client_pii` | third-party personal data: leads, prospects, replies, setters, suppression list, every `ws_*` and `ffm_*` table, `client_workspaces` | **never exported** |
| `secret` | push keys and endpoints | **never exported** |
| unclassified | a table nobody has classified yet | **not exported** (fail closed) until classified in a migration |

Decided by `public.backup_export_policy()` (table NAMES only, never data). Rules, in order of strength:
1. **Deny always wins.** `ws_*`, `ffm_*`, `client_workspaces` are denied by name pattern whatever any list says.
2. **Foreign-key closure.** A table with a foreign key to a non-exported table is not exported (a restore would otherwise load rows that point at missing data).
3. **Column drift.** A table on the allow side that gains a column that looks like personal contact data (email, phone, name, address, payee, birth…) and is not on the reviewed exception list (`backup_pii_column_exceptions()`) is excluded until reviewed.
4. **Second lock in code.** `hq_backup.py` re-checks every table against its own pattern (`ALWAYS_EXCLUDE`) and refuses to write a file if one gets through. It also refuses to run at all if the database function is missing or returns an unexpected result; there is no built-in "export everything" fallback.

The schema (structure, no rows) of every table, excluded ones included, is in the backup so a restore rebuilds the empty tables. The manifest lists what was excluded and why.

## 2. What this does NOT protect (read this before relying on it)
- **The live database and the database provider's own backups still contain client data.** This policy governs only the encrypted off-site file. Provider backups follow the provider's retention.
- **Client text in exported tables: what is CLOSED and what is NOT (Nov 15 2026, owner decision (a)+(b): fix at source AND redact at export; not live until the `20261120_*` migrations are released).**
  - **CLOSED (tested, see section 6):**
    - *Every text-like column of every exported table is classified, by construction.* `backup_effective_spec()` enumerates all text / varchar / jsonb / json / text[] / enum columns of the exported tables from the catalogue (92 LIGHT, 26 STRICT, 134 KEEP, 1 BLANK across 48 tables on the scratch replica). A column that is not in the reviewed list is treated as STRICT, reported in `redaction.unclassified_columns`, and a sqltest (`F1`, `F3`, `F7`) fails if any exported text-like column is unclassified. Each row carries a one-line reason. STRICT: `audit_log.detail`, `ledger.note`, `tasks.result`, `agent_runs.summary`, `escalations.summary`, `action_log.reason/detail/result/evidence`, `web_messages.body/payload`, `bank_transactions.description/note` (payer and payee names), `payment_instructions.payee`, `missions.title/objective/evidence/plan/checkpoint`, `ideas.description/result`, `owner_messages.answer/options`, `approval_requests.recommendation`, `reconciliation_flags.detail`, `executor_runs.refusal_reason`. LIGHT (patterns and known names, never blanks): titles, notes, purposes and other prose. KEEP: ids, codes, statuses, hashes, and unique keys (`audit_log.target`, `action_log.ref`, `tasks.dedupe_key`...). `evidence_sources.final_url` (the fetched URL) is LIGHT like its twin `url` that a restore or a lookup depends on and that code, not a person, writes. BLANK: `evidence_sources.text` (up to 40k characters of public web pages per row, rebuildable by fetching again; exported as an empty string, its sha256 and url stay; restore accepts it).
    - *Column types.* A column whose type the redactor does not read (bytea, name, xml, tsvector, composite, "char", jsonb[], inet, domain over json, arrays of enums or domains, ranges...) makes its TABLE unclassified: it is not exported and is listed in `backup_export_policy()->unclassified` (`backup_type_ok()`; sqltest K covers each type). Handled: text-like, json/jsonb, enums, text arrays, domains over text, and types that cannot carry a name (numbers, booleans, uuid, date/time, money, arrays of those).
    - *Known names, emails and phones* of every lead, setter, ws_lead, client workspace and setter-event client are removed from STRICT and LIGHT columns (case-, accent- and look-alike-insensitive; the narrowed per-snapshot context keeps the squashed form of EVERY live name, so `p i c a r d e a u`, `jpicardeau`, `picardeau1`, `the Picardeaus` and `T r e m b l a y` are caught exactly as by a direct call, in values AND JSON keys of strict columns, through `backup_snapshot()` and the paged export (sqltest J); `tel:613-555-0199`, `x613.555.0199`, `z.o.r.b.a.t.r.o.v`, `z_o_r_b_a_t_r_o_v`, `zorba.trov`, `b-o-b-n-g` included; the "short lower-case code" shortcut now runs only after those checks).
    - *Names the database no longer knows.* A persistent deny-list `ffm_redaction_denylist` holds keyed hashes (HMAC-SHA256, key in `ffm_redaction_keys`, generated inside the migration, never exported or logged) of normalised name tokens, squashed full names, emails and phone endings. Triggers on every client table capture the value BEFORE an erase, update or delete (`ffm_erase_lead`'s `[erased]` overwrite, `delete from leads`, TRUNCATE); the list is append-only (update/delete/truncate refused) and survives the rollback script. At export a set-based scan hashes the candidate tokens of the exported text and joins them to the list; matches are redacted exactly like live names. The list is `client_pii`/secret: not in the off-site file, not readable by anon/authenticated/service_role. Erased and deleted names are matched in the same forms as live ones: the capture stores the keyed hash of every name token and of its squashed form, and the export scan also tries each token with 1-2 characters added or removed at either end, with trailing / leading digits removed, and with letter-spaced / dotted / hyphenated windows (sqltest N: 25 forms x 2 names x 8 strict columns, single statement and paged: `Brackenridge`, `B r a c k e n r i d g e`, `b.r.a.c.k...`, `Brackenridge1`, `Brackenridge2024`, `the Brackenridges`, `obrackenridge`, `www.brackenridge.ca`, `OttolineBrackenridge`, `Brackenridge, Ottoline`, `BRACKENRIDGE`, accented, Cyrillic look-alike, zero-width, JSON keys and arrays). Names of 2 or more characters in a non-ASCII script (`李伟`, `김민`, `محمد`) are redacted; the 3-character floor applies to ASCII tokens only, and a two-part name is matched in either order (`Li, Wu`, `Xu Jo`). **No service_role-reachable function takes SQL text and runs it with the owner's rights, and none returns the pads:** `backup_deny_run(text, text)` is SECURITY INVOKER (it runs with the caller's rights, so as service_role it cannot read the key or the deny-list, nor write to it), the pads are derived inside the definer functions `backup_deny_terms` / `backup_deny_scan` and never travel in a context, argument or result (`backup_redaction_context()` no longer has a `pads` entry), and sqltest M calls every `backup_*` / `redaction_*` function as service_role after the lockdown migration with harmless and with hostile arguments (key-reading SQL, a poison-pill capture) and asserts no key bytes or 64-hex values come back, the deny-list count and the key table are unchanged. **Residual, harmless:** `backup_deny_terms(text, jsonb)` and `backup_redaction_context()` are callable by service_role; the first tells a caller which strings of ITS OWN input are on the deny-list (a membership oracle on text it already holds, no hashes, no key), the second returns the live names that service_role can read from `leads` anyway. The pad function and the capture function are SECURITY INVOKER on purpose: the lockdown migration (last) grants execute on every function to service_role, so a definer function would be callable; as invoker they need table access that only the owner has (sqltest L runs after lockdown and tests it as service_role). Growth: about 3-8 rows per person (about 100 bytes each); no retention limit by design (a name must stay recognisable for as long as an old backup or old text exists): it is bounded by the number of people ever stored, and an owner who must remove a person from it has to do so with a reviewed migration.
    - *JSON numbers.* `{"ph":6135550199,"ssn":123456789}` is no longer exported intact: under a PII-like key (phone, tel, ssn, sin, dob, card, account...) any number is replaced, and an integer of 7+ digits is replaced unless its key is on the amount allow-list (`amount`, `cents`, `total`, `count`, `qty`, `price`, `txid`, `seq`, `bytes`, `ms`...). A number that equals a known live phone (7-10 digits compared on the right-hand end) is replaced under ANY key, including `amount` / `total` (sqltest P); a phone that is only on the deny-list and sits in a JSON number under an allow-listed key is NOT caught (the number is not scanned against the deny-list). Numeric COLUMNS (amounts, counts) are never touched. The Python lock (`hq_backup.assert_redacted`) applies the same rule to numbers and the email/phone rules to strings, on every STRICT column the snapshot's own spec lists.
    - *Source writers.* Besides the writers fixed earlier (`record_lead_reply`, `mark_do_not_contact`, `setter_record_payout`, `set_deal_stage`, `confirm_deal_won`, the `agent_runs` trigger), `/in` and `/out` now store only a category word (`commission`, `hosting`, `ads`...) in `ledger.note` and say so when the memo is dropped, and "Paid deal" stores `Paid deal <n> of <date>` (a count), never the name typed; amount, kind, venture and day are unchanged. Task titles and details (`tasks.title/detail`) are the owner's own instructions to agents and are not rewritten at source; they are LIGHT/redacted at export.
    - *Engine storage keeps working.* `hq_scrub.scrub_stored` removes direct contact data (emails, phones, SIN-like numbers of 9+ digits, known client names, personal-profile and handle URLs, URLs carrying an email, phone or known name) but keeps ordinary URLs (`https://example.ca/staff/directory`), amounts and JSON numbers, so mission evidence extraction and the auditor's attached research still work (tested end to end). The export layer stays strict and authoritative. **Looseness of source mode:** URLs are kept unless they carry an email, phone, known name or a recognised profile/handle shape, so an unknown person's calendly.com / about.me / personal-site / CV URL survives the scrub; the export keeps it too unless it matches a pattern (light and strict redact only patterns and known names). Treat URLs of private individuals in task results as exported.
    - *Fail closed.* The whole field becomes `[redacted:uncertain]` when the sensitive-data detector flags it (health, income, banking, credit, identity-document terms), when it is longer than the limit (500 chars per JSON string / `ledger.note`, 20000 `tasks.result`, 4000 summaries), when decoding does not settle, when a known name or phone survives only in letter-spaced / split / ROT13 / reversed form, or on any internal error. A field in which nothing is found is exported unchanged.
    - *Code lock (`hq_backup.py`).* A snapshot without the version-2 redaction block is refused, not downgraded; after redaction any email, phone-shaped string or contact-like JSON number in a STRICT column makes the backup refuse to be written, and the error names table.column and a count, never a value. The database applies the same final tests last, so the lock is a backstop that should not trip. The two-read fallback (only if the database function is missing) exports no string outside the spec's KEEP columns (`hq_backup_keep.py`, generated from the spec; a unit test fails when stale), so strict, light, blank and unclassified columns are all blanked; inside a non-KEEP JSON value the object KEYS become positional markers (`[redacted:key0]`...), numbers of 7+ digits become 0, small numbers and booleans keep their value (structure kept), and `assert_redacted` runs on the fallback output too.
  - **NOT closed (limits that remain; read these):**
    0. *The topic detector over-blanks operational phrasings in STRICT columns (OWNER DECISION).* The detector is the exact twin of `ws_sensitive_hits()` (pinned by md5, so the two cannot drift) and fails closed on health, income, banking, credit and identity-document stems. In an ops line these are blanked: `income summary`, `Health check of scraper`, `Clinic Cleaning invoice`, `tax return reminder`, `T4 slip`. Narrowing a safety detector is an owner call and was not done; the cost is lost text in the off-site copy (ids, amounts and states are kept).
    1. *A person the database never held* (typed into a research result, a mission, a chat message) is not found by name; only their email, phone, handle and profile URL are removed. Names are matched only for people who were in `leads`, `setters`, `ws_leads`, `client_workspaces` or `setter_events` at some time after the deny-list triggers were installed. **People deleted before the triggers existed are not on the list** (an owner-authorised one-time seed from provider backups is needed; none was done).
    1b. *The capture triggers do not fire* under `session_replication_role = replica`, `pg_restore --disable-triggers`, or a COPY that disables triggers: values written or removed that way are not captured. Names that appear only in FREE-TEXT notes (not in the registered name/email/phone columns of leads, setters, ws_leads, client_workspaces, setter_events, contact_suppressions, outbox.to_ref) are never captured either.
    2. *Usefulness cost for common words.* A person called Sam, Pat or Bob makes every `sam`, `pat` or `bob` in STRICT text a redaction, and a company called Acme or Premier redacts those words. Name parts under 3 letters and a stop-list of industry words are not used. A common first name, once captured, over-redacts permanently (the list is append-only). This is deliberate (fail closed) and shows up as `[redacted:name]` in an otherwise normal sentence.
    3. *Pattern limits.* Mixed digit/word phones ("six one 3 555..."), leetspeak names (`z0rbatr0v`), short base64 (under 16 characters), base32, misspellings, scripts not mapped, ROT13 of names that are not known clients, and look-alikes outside the mapped Cyrillic/Greek/small-capital/NFKC set are not recognised. A never-live, DELETED name glued to a long alphabetic prefix or suffix (`brackenridgeville`, `chandrasekarancontracting`: more than 2 characters added) is not recognised from the deny-list (live names are, by the squashed check); digits, a plural and 1-2 letters are.
    4. *LIGHT columns* only remove patterns and whole known names (no letter-spaced / glued / digit / plural check; a spaced name survives there; **OWNER DECISION**: the agent-written LIGHT columns `owner_messages.body`, `missions.result`, `memory.content`, `escalations.evidence`, `tasks.title`, `tasks.detail` could be promoted to a squash-checked mode, at the price of more `[redacted:uncertain]` in prose and a changed 92 LIGHT / 134 KEEP split; not done here because it changes what a restore returns for those columns): a never-known name in `memory.content`, `ideas.name`, a title or a note survives. Prose in a KEEP column is not touched (KEEP is for codes; the reason on each row says why).
    5. *Detector-flagged or over-length text is lost* from the off-site copy (that is the point), including topic-heavy `tasks.result` (health, income, credit words). A restore loses redacted text by design; ids, amounts and states restore exactly. `evidence_sources.text` is not restored (re-fetch).
    6. *Old rows and old files.* The live database, provider backups, and anything exported earlier are unchanged; a one-time scrub of existing rows is an owner-authorised production change, not done here. `ffm_erase_lead`'s free-text reason in `audit_log.detail` is covered by the export, not changed at source.
    7. *Volume (re-measured alone on the idle 2-core scratch machine after the round-3 changes, which touch the deny-list scan on the hot path).* One `backup_snapshot()` statement for 50,284 audit rows + 10,026 tasks of 11.5k characters (131 M strict characters) took **175 s** (it was 155 s before round 3: the extra prefix/suffix, digit and CJK candidates cost about 13 %); a reviewer may see more with parallel load: expect 150-200 s, i.e. OVER the 120 s statement_timeout. The paged export of the same data (200-row pages, 1,000 for audit_log) took **174 s of page calls, worst single call 2.6 s**, plus the raw digests, so every statement stays far under 120 s. The target of 50k + 10k in under 60 s is NOT met (about 2.7 ms per task row of 11.5k characters is the regex work; the machine has 2 cores). Production today (303 audit rows, 183 tasks) is about 2 s. `hq_backup.py` asks `backup_snapshot_cost()` (recalibrated to the new constant: estimate about 174 s vs 175 s measured) and pages when the estimate exceeds **40 s** (so the single-statement mode never exceeds about 60 s even at 1.5x load); paging reads each table between two identical raw digests (`backup_table_digest`); a table that changes while it is read is flagged `consistent: false`. The single-statement consistency claim holds only in the single-statement mode. `scripts/perf_redaction.sh` measures it (the replica gate runs it with a 60 s budget on 2,000 + 200: about 5 s).
- **Column-drift heuristic is best-effort.** It misses names such as `phonenumber`, `contact_name`, `surname`, `cell`, `telephone`, `street`, `postal_code`, `sin`, `msisdn`, `notes`, `recipient`, `customer`. The real control is that every table must be classified by a human in a migration.
- **Restore gap.** After a restore from an off-site file, every client table is EMPTY, including `contact_suppressions`. Before any outreach is ever enabled, the opt-out list must be restored from the provider backup. Never contact anyone from a restored database until that is done.
- **`BACKUP_KEY` / bucket policy** (rotation, who may read, retention) are OWNER decisions not made here. Backblaze is not activated and no key exists.
- Classification is a reviewed list. A mistake there (a client table labelled `internal` and with no suspicious column names) would be exported. The code lock in rule 4 covers the known client table names only. This is why a human review is required when a table is added.

## 3. Consent log (decision A)
- `ffm_consent_log` is append-only and immutable (trigger; `service_role` has no write grants). A withdrawal is a new row, never an update.
- `ffm_can_contact(lead, channel)` is default-deny. True only with a current express consent, or an implied consent inside an owner-set window (`ffm_set_implied_window`, owner-only; unset = implied consent not accepted). A withdrawal (channel or `all`), a suppression hit, a closed workspace, an unknown lead or channel give false. Withdrawal is final in v1. An email or `all` withdrawal (and erasure) also adds the normalized address to `contact_suppressions`, so re-adding the same person as a new lead (case or `+tag` variants included) is still refused. Phone/SMS withdrawals follow the lead id only: a re-added lead with the same phone number is NOT blocked (known gap; no phone suppression list exists).
- **It authorizes nothing.** A true answer is necessary, never sufficient, for outreach. FF Marketing stays dry-run (CHECK-constrained); `ffm_route_preview` now refuses a lead with no current consent.
- `evidence_ref` is a short pointer (form id, message id), screened like all `ffm_*` text. Not a place for conversations.
- **Limit: the bot can record consent.** `ffm_record_consent` is callable by the service role with any evidence pointer of 3+ characters; nothing verifies the evidence. A compromised or mistaken bot could record express consent.
- **What counts as implied consent, and for how long: OWNER/COUNSEL.** No number is chosen in code. Whether the lead sources used actually give lawful consent (CASL in Canada, and any other jurisdiction) is a legal question this log records but cannot answer.

## 4. Erasure
`ffm_erase_lead` (owner-only): records a withdrawal for all channels, redacts name/email/phone/source/note on the lead, blanks consent `evidence_ref`, overwrites the free-text `source` on the lead's consent rows with `[erased]`, and keeps the metadata rows (basis, channel, times, lead uuid) so withdrawals survive without personal data. Because client PII is not in the off-site file, erasure has no external copy to chase for client data. Copies in provider backups expire under the provider's retention.

## 5. Sensitive-data detector, health terms (decision B)
`ws_sensitive_hits` gains a `health` category: a fail-closed screen with a long-stem substring list plus a short-word list with separator tolerance. **Limits (stated plainly):** regular-expression list, not a classifier. Misses misspellings, other languages, leetspeak, euphemisms and anything not listed. Refuses innocent text (listed false positives in `sqltests/ffm_consent_check.sql` section H; e.g. a substring can straddle a word boundary). **Confirmed bypasses (review):** Cyrillic look-alike letters, accented forms (`diábetes`), French (`diabète`); plain words not on the list (fracture, pain, pills, cough, flu, rehab, counsellor, sober, pregnancy wording). **Operational false positives:** "Medicine Hat", "health insurance", "disability insurance", "critical illness" are refused, so ordinary copy for the insurance client (Client 2) cannot use those phrases ("life insurance" passes). OWNER: decide how to describe those products. It reduces accidental capture; it does not make health data lawful to hold, and no health data should be collected for FF Marketing at all.
