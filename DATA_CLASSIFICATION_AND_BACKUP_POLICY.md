# Data classification, off-site backup and consent — policy as built

Status: ENGINEERING POLICY IMPLEMENTED IN CODE (dev branch, migrations NOT applied to production; leak-path redaction added Nov 15 2026). Not legal advice. Items marked OWNER/COUNSEL are decisions this document does not make.
Owner decisions this implements (Nov 2026): A consent log, B health terms in the sensitive-data detector, C no client lead PII in off-site backups, D backups only after exclusions are verified.

## 1. What leaves the database, and what never does

| Class | Meaning | Off-site backup |
|---|---|---|
| `public` | non-personal reference data (e.g. published model prices) | exported |
| `internal` | the owner's and the ventures' operating data | exported |
| `client_pii` | third-party personal data: leads, prospects, replies, setters, suppression list, every `ws_*` and `ffm_*` table, `client_workspaces` | **never exported** |
| `secret` | push keys and endpoints | **never exported** |
| unclassified | a table nobody has classified yet | **not exported** (fail closed) until classified in a migration |

Decided by `public.backup_export_policy()` (table NAMES only, never data). Rules, in order of strength:
1. **Deny always wins.** `ws_*`, `ffm_*`, `client_workspaces` are denied by name pattern whatever any list says.
2. **Foreign-key closure.** A table with a foreign key to a non-exported table is not exported (a restore would otherwise load rows that point at missing data).
3. **Column drift.** A table on the allow side that gains a column that looks like personal contact data (email, phone, name, address, payee, birth…) and is not on the reviewed exception list (`backup_pii_column_exceptions()`) is excluded until reviewed.
4. **Second lock in code.** `hq_backup.py` re-checks every table against its own pattern (`ALWAYS_EXCLUDE`) and refuses to write a file if one gets through. It also refuses to run at all if the database function is missing or returns an unexpected result; there is no built-in "export everything" fallback.

The schema (structure, no rows) of every table, excluded ones included, is in the backup so a restore rebuilds the empty tables. The manifest lists what was excluded and why.

## 2. What this does NOT protect (read this before relying on it)
- **The live database and the database provider's own backups still contain client data.** This policy governs only the encrypted off-site file. Provider backups follow the provider's retention.
- **Client text in exported tables: what is CLOSED and what is NOT (Nov 15 2026, owner decision (a)+(b): fix at source AND redact at export; not live until the `20261120_*` migrations are released).**
  - **CLOSED (tested, see section 6):**
    - *Every text-like column of every exported table is classified, by construction.* `backup_effective_spec()` enumerates all text / varchar / jsonb / json / text[] / enum columns of the exported tables from the catalogue (91 LIGHT, 26 STRICT, 135 KEEP, 1 BLANK across 48 tables on the scratch replica). A column that is not in the reviewed list is treated as STRICT, reported in `redaction.unclassified_columns`, and a sqltest (`F1`, `F3`, `F7`) fails if any exported text-like column is unclassified. Each row carries a one-line reason. STRICT: `audit_log.detail`, `ledger.note`, `tasks.result`, `agent_runs.summary`, `escalations.summary`, `action_log.reason/detail/result/evidence`, `web_messages.body/payload`, `bank_transactions.description/note` (payer and payee names), `payment_instructions.payee`, `missions.title/objective/evidence/plan/checkpoint`, `ideas.description/result`, `owner_messages.answer/options`, `approval_requests.recommendation`, `reconciliation_flags.detail`, `executor_runs.refusal_reason`. LIGHT (patterns and known names, never blanks): titles, notes, purposes and other prose. KEEP: ids, codes, statuses, hashes, and unique keys (`audit_log.target`, `action_log.ref`, `tasks.dedupe_key`, `evidence_sources.final_url`...) that a restore or a lookup depends on and that code, not a person, writes. BLANK: `evidence_sources.text` (up to 40k characters of public web pages per row, rebuildable by fetching again; exported as an empty string, its sha256 and url stay; restore accepts it).
    - *Known names, emails and phones* of every lead, setter, ws_lead, client workspace and setter-event client are removed from STRICT and LIGHT columns (case-, accent- and look-alike-insensitive; `tel:613-555-0199`, `x613.555.0199`, `z.o.r.b.a.t.r.o.v`, `z_o_r_b_a_t_r_o_v`, `zorba.trov`, `b-o-b-n-g` included; the "short lower-case code" shortcut now runs only after those checks).
    - *Names the database no longer knows.* A persistent deny-list `ffm_redaction_denylist` holds keyed hashes (HMAC-SHA256, key in `ffm_redaction_keys`, generated inside the migration, never exported or logged) of normalised name tokens, squashed full names, emails and phone endings. Triggers on every client table capture the value BEFORE an erase, update or delete (`ffm_erase_lead`'s `[erased]` overwrite, `delete from leads`, TRUNCATE); the list is append-only (update/delete/truncate refused) and survives the rollback script. At export a set-based scan hashes the candidate tokens of the exported text and joins them to the list; matches are redacted exactly like live names. The list is `client_pii`/secret: not in the off-site file, not readable by anon/authenticated. Growth: about 3-8 rows per person (about 100 bytes each); no retention limit by design (a name must stay recognisable for as long as an old backup or old text exists): it is bounded by the number of people ever stored, and an owner who must remove a person from it has to do so with a reviewed migration.
    - *JSON numbers.* `{"ph":6135550199,"ssn":123456789}` is no longer exported intact: under a PII-like key (phone, tel, ssn, sin, dob, card, account...) any number is replaced, and an integer of 7+ digits is replaced unless its key is on the amount allow-list (`amount`, `cents`, `total`, `count`, `qty`, `price`, `txid`, `seq`, `bytes`, `ms`...). Numeric COLUMNS (amounts, counts) are never touched. The Python lock (`hq_backup.assert_redacted`) applies the same rule to numbers and the email/phone rules to strings, on every STRICT column the snapshot's own spec lists.
    - *Source writers.* Besides the writers fixed earlier (`record_lead_reply`, `mark_do_not_contact`, `setter_record_payout`, `set_deal_stage`, `confirm_deal_won`, the `agent_runs` trigger), `/in` and `/out` now store only a category word (`commission`, `hosting`, `ads`...) in `ledger.note` and say so when the memo is dropped, and "Paid deal" stores `Paid deal <n> of <date>` (a count), never the name typed; amount, kind, venture and day are unchanged. Task titles and details (`tasks.title/detail`) are the owner's own instructions to agents and are not rewritten at source; they are LIGHT/redacted at export.
    - *Engine storage keeps working.* `hq_scrub.scrub_stored` removes direct contact data (emails, phones, SIN-like numbers of 9+ digits, known client names, personal-profile and handle URLs, URLs carrying an email, phone or known name) but keeps ordinary URLs (`https://example.ca/staff/directory`), amounts and JSON numbers, so mission evidence extraction and the auditor's attached research still work (tested end to end). The export layer stays strict and authoritative.
    - *Fail closed.* The whole field becomes `[redacted:uncertain]` when the sensitive-data detector flags it (health, income, banking, credit, identity-document terms), when it is longer than the limit (500 chars per JSON string / `ledger.note`, 20000 `tasks.result`, 4000 summaries), when decoding does not settle, when a known name or phone survives only in letter-spaced / split / ROT13 / reversed form, or on any internal error. A field in which nothing is found is exported unchanged.
    - *Code lock (`hq_backup.py`).* A snapshot without the version-2 redaction block is refused, not downgraded; after redaction any email, phone-shaped string or contact-like JSON number in a STRICT column makes the backup refuse to be written, and the error names table.column and a count, never a value. The database applies the same final tests last, so the lock is a backstop that should not trip. The two-read fallback (only if the database function is missing) blanks every free-text column named in the review instead of exporting it.
  - **NOT closed (limits that remain; read these):**
    1. *A person the database never held* (typed into a research result, a mission, a chat message) is not found by name; only their email, phone, handle and profile URL are removed. Names are matched only for people who were in `leads`, `setters`, `ws_leads`, `client_workspaces` or `setter_events` at some time after the deny-list triggers were installed. **People deleted before the triggers existed are not on the list** (an owner-authorised one-time seed from provider backups is needed; none was done).
    2. *Usefulness cost for common words.* A person called Sam, Pat or Bob makes every `sam`, `pat` or `bob` in STRICT text a redaction, and a company called Acme or Premier redacts those words. Name parts under 3 letters and a stop-list of industry words are not used. This is deliberate (fail closed) and shows up as `[redacted:name]` in an otherwise normal sentence.
    3. *Pattern limits.* Mixed digit/word phones ("six one 3 555..."), leetspeak names (`z0rbatr0v`), short base64 (under 16 characters), base32, misspellings, scripts not mapped, ROT13 of names that are not known clients, and look-alikes outside the mapped Cyrillic/Greek/NFKC set are not recognised.
    4. *LIGHT columns* only remove patterns and known names: a never-known name in `memory.content`, `ideas.name`, a title or a note survives. Prose in a KEEP column is not touched (KEEP is for codes; the reason on each row says why).
    5. *Detector-flagged or over-length text is lost* from the off-site copy (that is the point), including topic-heavy `tasks.result` (health, income, credit words). A restore loses redacted text by design; ids, amounts and states restore exactly. `evidence_sources.text` is not restored (re-fetch).
    6. *Old rows and old files.* The live database, provider backups, and anything exported earlier are unchanged; a one-time scrub of existing rows is an owner-authorised production change, not done here. `ffm_erase_lead`'s free-text reason in `audit_log.detail` is covered by the export, not changed at source.
    7. *Volume.* One `backup_snapshot()` statement costs about 1 ms per 1,000 STRICT characters plus 0.6 s fixed: measured 129 s for 50,284 audit rows + 10,026 tasks of 11.5k characters on the 2-core scratch machine (production today: 303 audit rows, 183 tasks, about 2 s). `hq_backup.py` asks `backup_snapshot_cost()` and above 60 s estimated pages the export (`backup_snapshot_page`, 200 rows per call, each call a few seconds) between two identical raw table digests (`backup_table_digest`); a table that changes while it is read is flagged `consistent: false` in the manifest. The single-statement consistency claim holds only for the single-statement mode. Scaling (scratch machine, single statement): 2,284 audit + 226 tasks 4.9 s; 12k audit + 1.2k tasks about 25 s (linear extrapolation, not measured); 50k + 10k 129 s; paged calls: 500 tasks 6.5 s, 5,000 audit rows 3.8 s. `scripts/perf_redaction.sh` measures it (the replica gate runs it with a 60 s budget on 2,000 + 200).
- **Column-drift heuristic is best-effort.** It misses names such as `phonenumber`, `contact_name`, `surname`, `cell`, `telephone`, `street`, `postal_code`, `sin`, `msisdn`, `notes`, `recipient`, `customer`. The real control is that every table must be classified by a human in a migration.
- **Restore gap.** After a restore from an off-site file, every client table is EMPTY, including `contact_suppressions`. Before any outreach is ever enabled, the opt-out list must be restored from the provider backup. Never contact anyone from a restored database until that is done.
- **`BACKUP_KEY` / bucket policy** (rotation, who may read, retention) are OWNER decisions not made here. Backblaze is not activated and no key exists.
- Classification is a reviewed list. A mistake there (a client table labelled `internal` and with no suspicious column names) would be exported. The code lock in rule 4 covers the known client table names only. This is why a human review is required when a table is added.

## 3. Consent log (decision A)
- `ffm_consent_log` is append-only and immutable (trigger; `service_role` has no write grants). A withdrawal is a new row, never an update.
- `ffm_can_contact(lead, channel)` is default-deny. True only with a current express consent, or an implied consent inside an owner-set window (`ffm_set_implied_window`, owner-only; unset = implied consent not accepted). A withdrawal (channel or `all`), a suppression hit, a closed workspace, an unknown lead or channel give false. Withdrawal is final in v1. An email or `all` withdrawal (and erasure) also adds the normalized address to `contact_suppressions`, so re-adding the same person as a new lead (case or `+tag` variants included) is still refused. Phone/SMS withdrawals follow the lead id only: a re-added lead with the same phone number is NOT blocked (known gap; no phone suppression list exists).
- **It authorizes nothing.** A true answer is necessary, never sufficient, for outreach. FF Marketing stays dry-run (CHECK-constrained); `ffm_route_preview` now refuses a lead with no current consent.
- `evidence_ref` is a short pointer (form id, message id), screened like all `ffm_*` text. Not a place for conversations.
- **Limit: the bot can record consent.** `ffm_record_consent` is callable by the service role with any evidence pointer of 3+ characters; nothing verifies the evidence. A compromised or mistaken bot could record express consent.
- **What counts as implied consent, and for how long: OWNER/COUNSEL.** No number is chosen in code. Whether the lead sources used actually give lawful consent (CASL in Canada, and any other jurisdiction) is a legal question this log records but cannot answer.

## 4. Erasure
`ffm_erase_lead` (owner-only): records a withdrawal for all channels, redacts name/email/phone/source/note on the lead, blanks consent `evidence_ref`, overwrites the free-text `source` on the lead's consent rows with `[erased]`, and keeps the metadata rows (basis, channel, times, lead uuid) so withdrawals survive without personal data. Because client PII is not in the off-site file, erasure has no external copy to chase for client data. Copies in provider backups expire under the provider's retention.

## 5. Sensitive-data detector, health terms (decision B)
`ws_sensitive_hits` gains a `health` category: a fail-closed screen with a long-stem substring list plus a short-word list with separator tolerance. **Limits (stated plainly):** regular-expression list, not a classifier. Misses misspellings, other languages, leetspeak, euphemisms and anything not listed. Refuses innocent text (listed false positives in `sqltests/ffm_consent_check.sql` section H; e.g. a substring can straddle a word boundary). **Confirmed bypasses (review):** Cyrillic look-alike letters, accented forms (`diábetes`), French (`diabète`); plain words not on the list (fracture, pain, pills, cough, flu, rehab, counsellor, sober, pregnancy wording). **Operational false positives:** "Medicine Hat", "health insurance", "disability insurance", "critical illness" are refused, so ordinary copy for the insurance client (Client 2) cannot use those phrases ("life insurance" passes). OWNER: decide how to describe those products. It reduces accidental capture; it does not make health data lawful to hold, and no health data should be collected for FF Marketing at all.

## 6. Evidence this was verified (dev, scratch databases only)
- `scripts/backup_drill.sh`: real PostgREST-shaped calls against a scratch Postgres with the full migration set: encrypt, upload to a fake B2, restore with the read-only key, row-for-row compare. Check P1: no client table file in the archive and none of the seeded lead names, emails or phone numbers appear in any data file. Check P2: the manifest lists `leads` as excluded and the schema still rebuilds it. Restore reports client tables as "absent from backup, as required"; a client table present in a backup is reported as a policy violation.
- Check P3 (added Nov 15): client names, emails and phone numbers seeded THROUGH `record_lead_reply`, `mark_do_not_contact`, `setter_record_payout`, the deal functions, researcher-style task results (scrubbed, raw and encoded), an escalation and `agent_runs` (one row with the source trigger bypassed) must not appear anywhere in the decrypted backup (data, schema, manifest); P4-P8 prove ledger counts/sums, audit row counts/actions and task ids are intact and the manifest records the redaction.
- `sqltests/backup_exclude_check.sql`, `sqltests/ffm_consent_check.sql`, `sqltests/leak_redaction_check.sql` (source writers, ~115 redactor vectors incl. encodings, look-alikes, French and adversarial splitting, indirect propagation, integrity, spec completeness F, review findings 1/3/4 G, deny-list H, cheap-path equivalence and paged export I), `test_hq_scrub.py`, `test_hq_backup.py`, `test_restore_backup.py`.
- These are synthetic tests. They are not production proof; production proof requires applying the migrations under a separate release authorization and running the post-release checks.

## 7. Before any off-site backup is activated (all required)
1. Migrations `20261119_ffm_consent_v1` and `20261119_backup_exclude_client_pii_v1` applied to production under release authorization; `select public.backup_export_policy()` reviewed by the owner (every `exported` table is expected to hold no client data; `unclassified` should be empty).
2. Owner sets retention and who may hold `BACKUP_KEY`; key generated by the owner (`ops/generate_backup_key.html`), never by Claude.
3. Backblaze account, bucket and a write-only key (and a separate read-only restore key) created by the owner.
4. Migrations `20261120_backup_redact_leak_paths_v1` and `20261120_leak_source_prevention_v1` applied (release authorization) and `ops/backup_activation_preflight.sh --require-pii-exclusion` passes (it reads `backup_export_policy()` and `backup_redaction_status()`: the leak paths are closed, not accepted), then one manual backup and one restore drill into a scratch database.

Rollback of the leak-path fixes: `ops/rollback_leak_redaction.sql` (restores the live definitions exactly; drilled in `scripts/replica/run.sh`; while it is in effect `hq_backup.py` refuses to export). Rollback: `ops/rollback_ffm_consent_backup.sql` (drops the consent log — irreversible loss of consent history — and restores the previous functions; the old `backup_snapshot` exports client data, so no off-site backups while it is in effect).
