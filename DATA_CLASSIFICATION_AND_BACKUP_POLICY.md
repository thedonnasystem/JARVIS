# Data classification, off-site backup and consent — policy as built

Status: ENGINEERING POLICY IMPLEMENTED IN CODE (dev branch, migrations NOT applied to production; leak-path redaction added Nov 15 2026). Not legal advice. Items marked OWNER/COUNSEL are decisions this document does not make.
Owner decisions this implements (Nov 2026): A consent log, B health terms in the sensitive-data detector, C no client lead PII in off-site backups, D backups only after exclusions are verified.

## 1. What leaves the database, and what never does

| Class | Meaning | Off-site backup |
|---|---|---|
| `public` | non-personal reference data (e.g. published model prices) | exported |
| `internal` | the owner's and the ventures' operating data | exported |
| `client_pii` | third-party personal data: leads, prospects, replies, setters, suppression list, every `ws_*` and `ffm_*` table, `client_workspaces` | **never exported** |
| `secret` | push keys and endpoints | **never exported** |
| unclassified | a table nobody has classified yet | **not exported** (fail closed) until classified in a migration |

Decided by `public.backup_export_policy()` (table NAMES only, never data). Rules, in order of strength:
1. **Deny always wins.** `ws_*`, `ffm_*`, `client_workspaces` are denied by name pattern whatever any list says.
2. **Foreign-key closure.** A table with a foreign key to a non-exported table is not exported (a restore would otherwise load rows that point at missing data).
3. **Column drift.** A table on the allow side that gains a column that looks like personal contact data (email, phone, name, address, payee, birth…) and is not on the reviewed exception list (`backup_pii_column_exceptions()`) is excluded until reviewed.
4. **Second lock in code.** `hq_backup.py` re-checks every table against its own pattern (`ALWAYS_EXCLUDE`) and refuses to write a file if one gets through. It also refuses to run at all if the database function is missing or returns an unexpected result; there is no built-in "export everything" fallback.

The schema (structure, no rows) of every table, excluded ones included, is in the backup so a restore rebuilds the empty tables. The manifest lists what was excluded and why.

The pad function and the capture function are SECURITY INVOKER on purpose: the lockdown migration (last) grants execute on every function to service_role, so a definer function would be callable; as invoker they need table access that only the owner has (sqltest L runs after lockdown and tests it as service_role). **Round 4:** `backup_deny_terms` and `backup_deny_scan` are SECURITY INVOKER too, so service_role gets NO deny-list answer from them or from `backup_redact_text(...,{"deny":true})` (they return null; a 50,000-word dictionary or 100,000 phone-shaped numbers gets nothing back; sqltest M12-M15). They run for the owner chain only (`backup_snapshot`, `backup_snapshot_page`, `backup_deny_prepare`, the triggers). **Residual oracle, stated plainly:** service_role can still INSERT exported text (for example a `tasks.result` holding a guessed name) and read `backup_snapshot()` / `backup_snapshot_page()` output, where a guessed erased name comes back as `[redacted:name]`. That is a guess-per-row oracle that costs a full export scan per query (25 s at 50k rows, 2 s today), not a bulk extractor, but it exists for as long as the bot's key can both write exported tables and call the export. Nothing in this repository removes that; the owner decision is to keep the export functions out of the bot's key (a separate backup role). `ffm_redaction_denylist_status()` (service_role may call it) returns row counts per kind, which discloses roughly how many people the system has ever known. **Dictionary poisoning:** the list is append-only and a name token of 3+ letters is redacted wherever it occurs; anyone who can INSERT a lead (service_role can) can add `Monday` or `Invoice` to it permanently, which over-redacts every backup from then on. The older definers `backup_schema`, `backup_classification` and `backup_pii_column_exceptions` and the five writers (`record_lead_reply`...) keep their original search paths; the CREATE revoke is what protects them. Growth: about 3-8 rows per person (about 100 bytes each); no retention limit by design (a name must stay recognisable for as long as an old backup or old text exists): it is bounded by the number of people ever stored, and an owner who must remove a person from it has to do so with a reviewed migration.
    - *JSON numbers.* `{"ph":6135550199,"ssn":123456789}` is no longer exported intact: under a PII-like key (phone, tel, ssn, sin, dob, card, account...) any number is replaced, and an integer of 7+ digits is replaced unless its key is on the amount allow-list (`amount`, `cents`, `total`, `count`, `qty`, `price`, `txid`, `seq`, `bytes`, `ms`...). Numeric COLUMNS (amounts, counts) are never touched. Task titles and details (`tasks.title/detail`) are the owner's own instructions to agents and are not rewritten at source; they are LIGHT/redacted at export.
    - *Engine storage keeps working.* `hq_scrub.scrub_stored` removes direct contact data (emails, phones, SIN-like numbers of 9+ digits, known client names, personal-profile and handle URLs, URLs carrying an email, phone or known name) but keeps ordinary URLs (`https://example.ca/staff/directory`), amounts and JSON numbers, so mission evidence extraction and the auditor's attached research still work (tested end to end). The export layer stays strict and authoritative. **Looseness of source mode:** URLs are kept unless they carry an email, phone, known name or a recognised profile/handle shape, so an unknown person's calendly.com / about.me / personal-site / CV URL survives the scrub; the export keeps it too unless it matches a pattern (light and strict redact only patterns and known names). Treat URLs of private individuals in task results as exported.
    - *Fail closed.* The whole field becomes `[redacted:uncertain]` when the sensitive-data detector flags it (health, income, banking, credit, identity-document terms), when it is longer than the limit (500 chars per JSON string / `ledger.note`, 20000 `tasks.result`, 4000 summaries), when decoding does not settle, when a known name or phone survives only in letter-spaced / split / ROT13 / reversed form, or on any internal error. A field in which nothing is found is exported unchanged.
    - *Code lock (`hq_backup.py`).* A snapshot without the version-2 redaction block is refused, not downgraded; after redaction any email, phone-shaped string or contact-like JSON number in a STRICT column makes the backup refuse to be written, and the error names table.column and a count, never a value. The database applies the same final tests last, so the lock is a backstop that should not trip. The two-read fallback (only if the database function is missing) exports no string outside the spec's KEEP columns (`hq_backup_keep.py`, generated from the spec; a unit test fails when stale), so strict, light, blank and unclassified columns are all blanked; inside a non-KEEP JSON value the object KEYS become positional markers (`[redacted:key0]`...), numbers of 7+ digits become 0, small numbers and booleans keep their value (structure kept), and `assert_redacted` plus `assert_no_digit_runs` (no run of 7+ digits in any blanked column, light ones included) run on the fallback output too; a string is kept only if it is a uuid, an ISO date / date-time with colons, or a number of at most 6 digits.

    0. *The topic detector over-blanks operational phrasings in STRICT columns (OWNER DECISION).* The detector is the exact twin of `ws_sensitive_hits()` (pinned by md5, so the two cannot drift) and fails closed on health, income, banking, credit and identity-document stems. Narrowing a safety detector is an owner call and was not done; the cost is lost text in the off-site copy (ids, amounts and states are kept).
    1. *A person the database never held* (typed into a research result, a mission, a chat message) is not found by name; only their email, phone, handle and profile URL are removed. Names are matched only for people who were in `leads`, `setters`, `ws_leads`, `client_workspaces` or `setter_events` at some time after the deny-list triggers were installed. **People deleted before the triggers existed are not on the list** (an owner-authorised one-time seed from provider backups is needed; none was done).
    1b. *The capture triggers do not fire* under `session_replication_role = replica`, `pg_restore --disable-triggers`, or a COPY that disables triggers: values written or removed that way are not captured. Names that appear only in FREE-TEXT notes (not in the registered name/email/phone columns of leads, setters, ws_leads, client_workspaces, setter_events, contact_suppressions, outbox.to_ref) are never captured either.
    2. *Usefulness cost for common words.* A person called Sam, Pat or Bob makes every `sam`, `pat` or `bob` in STRICT text a redaction, and a company called Acme or Premier redacts those words. Name parts under 3 letters and a stop-list of industry words are not used. A common first name, once captured, over-redacts permanently (the list is append-only). This is deliberate (fail closed) and shows up as `[redacted:name]` in an otherwise normal sentence.
    3. *Pattern limits.* Mixed digit/word phones ("six one 3 555..."), leetspeak names (`z0rbatr0v`), short base64 (under 16 characters), base32, misspellings, scripts not mapped, ROT13 of names that are not known clients, and look-alikes outside the mapped Cyrillic/Greek/small-capital/NFKC set are not recognised. An ERASED or DELETED name glued to a long alphabetic prefix or suffix (`brackenridgeville`, `chandrasekarancontracting`: more than 2 characters added) is not recognised from the deny-list (live names are, by the squashed check); digits, a plural and 1-2 letters are. A name whose tokens are 3-4 letters (`Li Wu`, `Ng`) gets no variant protection (only whole-token and whole-name matching); a 2-character ASCII surname on its own is never matched; a spaced CJK name (`李 伟`) and transliterations (`Li Wei` for `李伟`, `Mohammed` / `Muhammad`) are not recognised.
    4. *LIGHT columns* only remove patterns and whole known names (no letter-spaced / glued / digit / plural check), so they are NOT a guarantee. Round 5 (owner directive E) therefore holds only operator-authored configuration text in LIGHT; every column that an agent, a scraper, a client or a counterparty can write into is BLANK or STRICT (rule 8). Prose in a KEEP column is not touched (KEEP is for codes; the reason on each row says why). A new, unclassified text column is STRICT (fails closed).
    5. *Detector-flagged or over-length text is lost* from the off-site copy (that is the point), including, since round 5, ALL agent-written free text (rule 8 below). A restore loses redacted text by design; ids, amounts and states restore exactly. `evidence_sources.text` is not restored (re-fetch).
    6. *Old rows and old files.* The live database, provider backups, and anything exported earlier are unchanged; a one-time scrub of existing rows is an owner-authorised production change, not done here. `ffm_erase_lead`'s free-text reason in `audit_log.detail` is covered by the export, not changed at source.
    7. *Volume (re-measured alone on the idle 2-core scratch machine after round 5, when every agent-written free-text column became BLANK).* One `backup_snapshot()` statement for 50,284 audit rows (strict JSON detail, 10.7 M characters) + 10,026 tasks took **67-72 s** (it was 180 s in round 4, when 131 M characters of `tasks.result` went through the regexes; blanking removed them; the 11.5k-character task results now cost nothing). That is still above the 60 s target only marginally and below the 120 s statement_timeout in this run, but the cost is now per audit field (about 1.3 ms) and not per character. The paged export of the same data: whole-export deny-list scan once (`backup_deny_prepare()`, **5.8 s**) then 500-row pages: **71.6 s of page time in 195 calls, worst single call 0.9 s**, plus the raw digests and the epoch reads (a few ms). Production today (303 audit rows, 183 tasks) is about 1-2 s. `hq_backup.py` asks `backup_snapshot_cost()`; the estimate was re-calibrated in round 5 (74 s estimated vs 67-72 s measured; it over-counts cheap fields on purpose) and the export is paged when the estimate exceeds **40 s**. Paging reads each table between two identical raw digests (`backup_table_digest`) and the whole export between two identical epoch vectors (rule 9). `scripts/perf_redaction.sh` measures the single statement (the replica gate runs it with a 60 s budget on 2,000 + 200: about 5 s).
    8. *Free text is blanked, not trusted to a regex (round 5, item E).* Columns that agents, scrapers, clients or counterparties write are exported as an empty string (JSON `null` for json/array columns) and listed in `manifest.redaction.blanked_columns`. **What is lost off-site:** the text of tasks (title, detail, result), agent run summaries, memory content, owner messages and answers, mission results/plans/evidence, escalation summaries/evidence, action log text, web messages, bank descriptions/payees, idea text, approval recommendations and the fetched evidence page text. Ids, statuses, amounts, timestamps, hashes and foreign keys are kept, so counts, money and the shape of the history restore exactly. **Restore:** `ops/restore_backup.py` turns every blanked column into NULL when the column is nullable, otherwise `''` (text), `{}` (jsonb object default), `[]` (array), so NOT NULL and CHECK constraints are not broken; the report counts them in `blanked_fields_restored_empty`. Rebuilding the lost text is a provider-backup restore, not an off-site one. The privacy rule wins over completeness: nothing was weakened to make backups more complete.
    9. *Consistency (round 5, items A and B).* A file is uploaded only if `manifest.consistency.consistent is True`; `false`, missing or unknown status is refused in `hq_backup.run()`, in `verify()` and by the restore tool (`--allow-unverified` exists for a disaster restore and is reported). The single-statement export is one database snapshot. The paged export (and the fallback) prove themselves with an **epoch vector** `backup_epoch()` read before the first page and after the last: one counter (a sequence bumped by owner-only statement triggers on insert, update, delete AND truncate of every redaction source: leads, setters, setter_events, setter_payouts, ws_*, client_workspaces, lead_replies, deals, contact_suppressions, and on the deny-list), the row count of every source (catches writes made with triggers disabled), the deny-list row count, and md5 of EVERY function of the backup_* / redaction_* families plus the detector twin and the writer trigger (derived from the catalog by name, not a hand list) and of the full export spec (table list and every column's mode). Round 6: the bump is conditional (INSERT / DELETE only when a row was touched, UPDATE only when a redaction-source COLUMN of some row actually changed, via transition tables; 0-row statements, status / score / body updates and `on conflict do nothing` captures do not count; TRUNCATE always does), so continuous outreach writes to non-source columns cannot starve a paged backup; an outbox INSERT (a new recipient) or a source-column change still discards the archive and is retried (3 attempts), which at production volumes (a paged run takes seconds to minutes) is rare. Any difference discards the whole archive; the run retries up to 3 attempts, then fails: nothing is uploaded, the previous verified backup is untouched, the failure goes to `audit_log` and an owner message (once a day), and the next scheduled run retries. The fallback exporter is verified only by the same epoch (before == after, two identical reads); with the epoch function missing it refuses to upload. The sequence has no API privilege and `backup_epoch()` is service_role-executable but returns counters and hashes only.
    10. *Redaction cache (round 5, item C).* The paged export scans the live data once (`backup_deny_prepare()`) and pages reuse the result from `ffm_redaction_found`: an UNLOGGED table (so it is not in the WAL, nor in a physical backup of replicas), no API grant, excluded from the export by its `ffm_` name and by the policy, rows keyed by a random run uuid (`gen_random_uuid()`) bound to the caller (`role|session_user|jwt sub`). A page uses a row only for the matching caller, the matching run and a run younger than 20 minutes (binding: the caller is `role|session_user|jwt sub`, which through PostgREST is the same for every session of one role; the 122-bit run id is the real secret and can appear in PostgREST request logs, so since round 6 the stronger binding is that only the `backup_reader` identity can call prepare / release / page at all (rule 11); with the service key retained (rule 12 option C) another service_role session that learns a run id could release it, never read it); anything else (forged, another caller, expired, released) runs the whole scan, never skips it. `backup_deny_release(run)` deletes only that caller's run; `hq_backup.py` releases in a `finally` (success, failed page, exception). Rows older than the TTL are purged at every prepare and release, and by a pg_cron job (`ffm_redaction_found_purge`, every 15 minutes) when pg_cron exists; without pg_cron the per-call purge is the only cleanup and the documented scheduled task is: `select public.backup_deny_release();` hourly. Retention is minimal: the rows hold strings that already sit in the rows being exported, for at most 20 minutes (the export takes minutes; the bound is the paged run duration).
    11. *Owner-only helpers and the backup identity (round 6, item D).* `migrations/20261121_postlock_backup_identity_v1.sql` is ordered AFTER the lockdown on purpose (the lockdown ends with `grant execute on all functions in schema public to service_role`; only a later file can take that back; `scripts/lint_migrations.py` R3 now allows only `postlock` files after it, and R4/R5 apply to them). It creates the NOLOGIN role `backup_reader` (no password, no BYPASSRLS, no table privilege at all: the reader functions are SECURITY DEFINER and read the data themselves), gives it EXECUTE on exactly 12 functions (`backup_schema`, `backup_export_policy`, `backup_snapshot`, `backup_snapshot_page`, `backup_table_digest`, `backup_snapshot_cost`, `backup_redaction_meta`, `backup_epoch`, `backup_deny_prepare`, `backup_deny_release`, `backup_redaction_status`, `redaction_denylist_status`) and revokes everything else named `backup_*` / `redaction_*` (45 owner-only helpers, plus `agent_runs_scrub`) and every privilege on `ffm_redaction_keys`, `_denylist`, `_found` and the epoch sequence from public, anon, authenticated and service_role. The rule is the catalogue (`select * from public.backup_acl_catalogue()`, owner only): a new helper that follows the naming rule is revoked automatically on the next apply. Defence in depth: every SECURITY DEFINER backup function that reads a key, the deny-list, the cache, the epoch or the exported data starts with `perform public.backup_assert_reader()`, which refuses a session whose role is anon / authenticated / service_role even when EXECUTE is granted, so re-running the lockdown's blanket grant (or a worse one to all three roles) cannot expose them (`sqltests/backup_identity_check.sql` D4). Not covered by the guard, by design: the pure text helpers (they read no data and no key; for them the revoke is the control and a blanket grant exposes them until the post-lockdown migration is applied again) and the table / sequence privileges (a body cannot guard a table; the revoke is re-applied by the migration). Both are caught by the committed post-lockdown ACL manifest `ops/ACL_MANIFEST_public.tsv` (every public function, table and sequence x anon, authenticated, service_role, backup_reader; same first seven columns as PR #20's `ops/ACL_MANIFEST_consent_v3.tsv`; `scripts/acl_manifest.py --check` is part of the gate's `manifest` step and also fails on any API-role privilege on a backup/internal object). `hq_backup.py` sends the token in `BACKUP_READER_JWT` for its RPC calls and never the service key; without the token the database refuses the backup after the migration (fail closed, nothing uploaded).
    12. *OWNER DECISION: how the backup identity reaches PostgREST (cannot be done from this repository).* PostgREST takes the database role from the `role` claim of a JWT signed with the project's JWT secret. `backup_reader` exists after the migration and is granted to `authenticator` (the migration prints a NOTICE if the hosted `postgres` role is not allowed to do that grant: run `grant backup_reader to authenticator;` in the SQL editor). What only the owner can supply is the token: (A) projects that still have the legacy HS256 JWT secret: mint a JWT `{"role":"backup_reader","iss":"supabase","iat":...,"exp":...}` with a long expiry and store it as `BACKUP_READER_JWT` next to `BACKUP_KEY` (it is a bearer secret for the backup functions only: it cannot read the key table, the deny-list, or any table, and the redacted export is what it returns; rotating it means minting a new one, rotating the project JWT secret invalidates every key, so avoid that); (B) projects on asymmetric signing keys (publishable / secret keys): a custom-role JWT cannot be minted without the private key, so use a direct database connection for the backup instead (`alter role backup_reader login password '<typed by the owner, never in the repo>'`, connect through the pooler, run the same twelve functions): `hq_backup.py` has no direct-database transport yet, that is a follow-up build; (C) if neither is acceptable: do NOT apply the post-lockdown migration; the backup then runs with the service key as today, the guard and the revokes are absent and a service key leak can run every backup function (the key table stays ungranted and no function returns the key: sqltests round 3 / 4). Until the owner chooses, applying the migration without the token only makes the backup refuse to run, which is the safe failure; `ops/backup_activation_preflight.sh` reports both halves. Not verified against a real PostgREST / Supabase (scratch Postgres only): the role switch is exercised with `SET ROLE`, which is what PostgREST does.
    13. *Residual risks the round-5 verifier listed (accepted, not hidden).* (E3) 75 of the 134 KEEP columns have no CHECK, FK or enum: `audit_log.actor/target/action`, `tasks.dedupe_key/created_by`, `memory.agent`, `action_log.ref/actor`, `approval_requests.ref`, `owner_messages.ref_table`, `evidence_sources.host_norm`. Repository writers store only system codes there, but any writer with the service key can put text there and it is exported untouched; the control is the writer review, not the export. (E4) `audit_log.detail` (STRICT) still receives owner / agent free text from `ffm_erase_lead(p_reason)`, `executor_request` and `set_venture_stage`: known, erased and deleted names and all patterns are removed, a third party's name that is in no table survives. Changing `ffm_erase_lead` to store a reason code needs a consent-stream migration (20261119_ffm_consent_v1 is applied elsewhere and owned by the consent line), so it is reported, not changed here; an owner decision. (E5) The off-site file is a disaster-recovery skeleton: agent working state is lost by design (rule 8). (B3) A privileged writer (the database owner) that sets `session_replication_role = replica` AND leaves every row count unchanged, or rewinds the epoch sequence, is not detected: that needs the owner's own credentials, which the backup protects against only by not handing them to the bot.
- **Column-drift heuristic is best-effort.** It misses names such as `phonenumber`, `contact_name`, `surname`, `cell`, `telephone`, `street`, `postal_code`, `sin`, `msisdn`, `notes`, `recipient`, `customer`. The real control is that every table must be classified by a human in a migration.
- **Restore gap.** After a restore from an off-site file, every client table is EMPTY, including `contact_suppressions`. Before any outreach is ever enabled, the opt-out list must be restored from the provider backup. Never contact anyone from a restored database until that is done.
- **`BACKUP_KEY` / bucket policy** (rotation, who may read, retention) are OWNER decisions not made here. Backblaze is not activated and no key exists.
- Classification is a reviewed list. A mistake there (a client table labelled `internal` and with no suspicious column names) would be exported. The code lock in rule 4 covers the known client table names only. This is why a human review is required when a table is added.

## 3. Consent log (decision A)
- `ffm_consent_log` is append-only and immutable (trigger; `service_role` has no write grants). A withdrawal is a new row, never an update.
- `ffm_can_contact(lead, channel)` is default-deny. True only with a current express consent, or an implied consent inside an owner-set window (`ffm_set_implied_window`, owner-only; unset = implied consent not accepted). A withdrawal (channel or `all`), a suppression hit, a closed workspace, an unknown lead or channel give false. Withdrawal is final in v1. An email or `all` withdrawal (and erasure) also adds the normalized address to `contact_suppressions`, so re-adding the same person as a new lead (case or `+tag` variants included) is still refused. Phone/SMS withdrawals follow the lead id only: a re-added lead with the same phone number is NOT blocked (known gap; no phone suppression list exists).
- **It authorizes nothing.** A true answer is necessary, never sufficient, for outreach. FF Marketing stays dry-run (CHECK-constrained); `ffm_route_preview` now refuses a lead with no current consent.
- `evidence_ref` is a short pointer (form id, message id), screened like all `ffm_*` text. Not a place for conversations.
- **Limit: the bot can record consent.** `ffm_record_consent` is callable by the service role with any evidence pointer of 3+ characters; nothing verifies the evidence. A compromised or mistaken bot could record express consent.
- **What counts as implied consent, and for how long: OWNER/COUNSEL.** No number is chosen in code. Whether the lead sources used actually give lawful consent (CASL in Canada, and any other jurisdiction) is a legal question this log records but cannot answer.

## 4. Erasure
`ffm_erase_lead` (owner-only): records a withdrawal for all channels, redacts name/email/phone/source/note on the lead, blanks consent `evidence_ref`, overwrites the free-text `source` on the lead's consent rows with `[erased]`, and keeps the metadata rows (basis, channel, times, lead uuid) so withdrawals survive without personal data. Because client PII is not in the off-site file, erasure has no external copy to chase for client data. Copies in provider backups expire under the provider's retention.

## 5. Sensitive-data detector, health terms (decision B)
`ws_sensitive_hits` gains a `health` category: a fail-closed screen with a long-stem substring list plus a short-word list with separator tolerance. **Limits (stated plainly):** regular-expression list, not a classifier. Misses misspellings, other languages, leetspeak, euphemisms and anything not listed. Refuses innocent text (listed false positives in `sqltests/ffm_consent_check.sql` section H; e.g. a substring can straddle a word boundary). **Confirmed bypasses (review):** Cyrillic look-alike letters, accented forms (`diábetes`), French (`diabète`); plain words not on the list (fracture, pain, pills, cough, flu, rehab, counsellor, sober, pregnancy wording). **Operational false positives:** "Medicine Hat", "health insurance", "disability insurance", "critical illness" are refused, so ordinary copy for the insurance client (Client 2) cannot use those phrases ("life insurance" passes). OWNER: decide how to describe those products. It reduces accidental capture; it does not make health data lawful to hold, and no health data should be collected for FF Marketing at all.
